# IEP — سعة التشغيل وإدارة المطعم

> تحديث المراجعة 2026-10-09: [التقرير الشامل والأدلة](PROJECT_REVIEW.md) هو مرجع الحالة الحالية؛ يسجل عيوبًا مفتوحة وأولويات إصلاح وخطة قبول. نجاح الاختبارات القائمة لا يغلق الحالات الجديدة.

هذه وثيقة قرار وتشغيل، وليست شهادة بأن النظام اجتاز تشغيلًا متواصلًا لمدة ٢٤ ساعة. الحسابات مبنية على نقطتي خروج ثابتتين: شباك أطباق بعرض يقارب مترًا، وبحد أقصى أربعة عناصر متزامنة، ونقطة مشروبات مشابهة. نبدأ بكاميرا واحدة لكل نقطة ونختبر الحجب قبل اعتماد عدد الكاميرات والأجهزة.

## ما يعمل الآن وما يحتاج تنفيذًا ميدانيًا

يمكن اختيار فيديو محلي وتحليل إطاراته وتسجيل تجارب منفصلة، وإضافة الأصناف والصور المرجعية، ومراجعة الأحداث ومقارنتها ببيانات الكاشير المدخلة أو المستوردة. التحليل الحالي يجري على جهاز المتصفح، والفيديو الكامل لا يرفع إلى الخادم ولا يسجل بواسطة هذا التطبيق. NVR يحتفظ بالفيديو؛ قاعدة SQLite تحفظ metadata ومراجع الصور، والصور المرجعية ولقطات الأحداث في adapter قرص خاص مستقل `IEP_MEDIA_DIR`؛ S3 ليس تكاملًا منفذًا. ملفات النماذج محلية. [متطلبات السحابة](CLOUD_REQUIREMENTS.md) تشرح خادم الويب مقابل عامل معالجة الفيديو.

توجد الآن أدوار محددة للمطاعم، إدارة مستخدمين، سجل مخاطر وتدقيق، اعتماد/إعادة فتح اليومية، تصحيحات أحداث مع حفظ الأصل، ومراجعة عبور مجهول. مفاتيح API محدودة بنطاقات ومطاعم ومدة ويمكن إلغاؤها، وواجهة الربط تعرض OpenAPI. هذه أدوات تشغيل ومراجعة داخل prototype، لا تعني اكتمال تكامل الكاشير أو خدمة معالجة الفيديو طويلة التشغيل. [المخاطر والصلاحيات](RISK_AND_ACCESS.md) و[دليل التكامل](INTEGRATION_GUIDE.md) يفصلان الحدود.

التجربة المحلية تدعم تحديد جزء من الفيديو وبصمة محسوبة على دفعات، وتحتفظ ببصمة manifest وإعدادات العد ومعرفات الصور المرجعية. طابور IndexedDB يكتب قبل إرسال الأحداث، ويعيد المحاولة تلقائيًا منفصلًا عن inference، بحد ١٠٠٠ حدث أو حجم JSON تقديري ٦٤MiB؛ يتوقف التحليل عند الامتلاء بدل إسقاط أحداث. مراقبة البث تتابع تقدم الإطارات نفسها وتبلغ stalled عند غيابها، لكن callbacks جديدة لصورة متكررة لا تثبت اكتشاف كل تجمد ممكن. المصنف لا يحفظ عنصرًا لم يكشفه إطلاقًا بمجرد وجود قائمة مجهول.

رفع فيديو طويل لا يحوله إلى نظام تشغيل مستمر. القراءة كل ٠٫٢ ثانية تعني هدف عينة مقداره ٥ إطارات/ثانية من **زمن الفيديو**؛ لا تعني أن الجهاز قادر على تحليل ٥ إطارات/ثانية فعلية. فك الفيديو والانتقال للإطار والتحليل وكتابة الأحداث تضيف وقتًا. تحليل البث الحي له مسار وجدولة مختلفان. تشغيل المتصفح على الموبايل يتأثر بقفل الشاشة والخلفية والحرارة والبطارية وإعادة تحميل الصفحة.

الحل النهائي يحتاج خدمة داخل المطعم تستقبل RTSP من الكاميرات/NVR وتعمل تلقائيًا مع بدء الجهاز، وتكتب الأحداث محليًا قبل الإرسال، وتستعيد التسجيل المتوفر بعد الانقطاع دون تكرار العد. موصل Hikvision وONVIF واسترجاع الفيديو وخدمة edge طويلة التشغيل وتسريع CUDA/GPU ليست وظائف مكتملة في هذه النسخة. يجب اختبار دقة الأطباق والمشروبات على فيديو مستقل؛ الكاشف العام والصور المرجعية لا يعادلان نموذجًا مدربًا لكل مطعم.

## اختبار السعة القابل للإعادة

السكربت `scripts/benchmark-capacity.mjs` ينشئ قاعدة بيانات مؤقتة ثم يحذفها؛ لا يستخدم بيانات تشغيل المطعم أو أسراره. يقيس API التقارير والمطابقة الفعليين عند ١٠٠ ألف ثم مليون حدث موزعة على ٢٠/٢٠٠ يوم، ٥٠٠٠ حدث يوميًا، و٢٠ صنفًا، **بلا صور أحداث**. يتحقق من أن إجمالي يوم الاختبار ٥٠٠٠، بينما قائمة التقرير افتراضيًا تعرض آخر ١٠٠٠ فقط. API يدعم صفحات ١–٢٠٠ حدث بمؤشر `nextCursor` للوصول للأقدم؛ `totals` يغطي الفترة كاملة مستقلاً عن الصفحة. قياس مليون صف ليس اختبار مليون طلب HTTP أو مليون صورة أو أداء عدة عملاء متزامنين.

عند توفير Playwright وChromium وملفات النماذج، يقيس MobileNet وCOCO الحقيقيين على إطار اصطناعي ٦٤٠×٣٦٠، مع أربع قصاصات لتقدير تكلفة تصنيف أربعة عناصر. لا يستبدل النماذج بكاشف وهمي. الإطار الاصطناعي لا يقيس صحة التعرف؛ تكلفة القصاصات الأربعة تُفرض حتى إذا لم يكتشف الكاشف أربعة عناصر. ينفذ دورة إحماء ثم خمس عينات لكل مسار CPU وWebGL المتاح. p95 من خمس عينات هو وصف لهذه العينة الصغيرة، وليس حدًا مضمونًا.

```sh
# من مجلد المشروع، بعد npm ci وتنزيل النماذج المحلية.
# IEP_BROWSER_EXECUTABLE اختياري لنسخة Chromium مثبتة على جهازك.
IEP_BROWSER_EXECUTABLE=/absolute/path/to/chromium \
IEP_BENCH_OUTPUT=/absolute/path/to/capacity-results.json \
npm run bench:capacity
```

Playwright تابع تطوير محلي يُثبت بواسطة `npm ci`، والمتصفح إما Chromium مثبت أو نسخة Playwright المجهزة. إذا تعذر بدء المتصفح يذكر السكربت أن inference لم يُقَس؛ لا تستنتج نتيجة نموذج من نتيجة قاعدة البيانات وحدها. عدد عينات النموذج قابل للتحديد بـ`IEP_BENCH_SAMPLES` بين ٣ و١٢. السكربت لا ينزل أدوات أو نماذج، ولا يحفظ كلمة المرور المؤقتة. النتائج JSON تحتوي مواصفات البيئة، أوقات العمليات، ذاكرة Node/TensorFlow، وبصمات النماذج المتوفرة. نفذ القياس على جهاز المطعم المرشح قبل شرائه نهائيًا.

### نتائج البيئة الحالية

نُفذ القياس المحدود بتاريخ ٢٠٢٦-١٠-٠٩ على Node ‏24.19.0، معالج AMD EPYC ‏9V74 افتراضي، ٥ أنوية ظاهرة وحصة cgroup تعادل **٤ أنوية**، وحد RAM ‏٣٢GiB؛ نحو ٢٩GiB مساحة عمل متاحة وقت الفحص. هذه بيئة تطوير سحابية وليست جهاز مطعم، ولا تحتوي القياسات على GPU فعلي: WebGL استخدم **SwiftShader برمجيًا**. النتائج خمس عينات بعد الإحماء، دون ضغط عملاء متزامنين.

| مسار النموذج الحقيقي | كشف إطار ٦٤٠×٣٦٠، متوسط | تصنيف قصاصة واحدة، متوسط | تصنيف ٤ قصاصات، متوسط | كشف +٤، متوسط / p95 |
|---|---:|---:|---:|---:|
| TensorFlow CPU | ١٦٧٦ms | ٧٢٩ms | ٢٩٦٨ms | ٤٦٤٣ / ٤٨٧٠ms |
| WebGL / SwiftShader برمجي | ٥٣٩ms | ٢٥٥ms | ٩٩٢ms | ١٥٣١ / ١٥٥٥ms |

**المسار الحالي لا يحقق ٥fps في هذه البيئة؛ حتى الكشف وحده يتجاوز ٢٠٠ms.** حد الأداء النظري عند أربع قصاصات يقارب ٠٫٢٢fps للـCPU و٠٫٦٥fps للـWebGL البرمجي قبل إضافة فك الفيديو والمطابقة والتسجيل. لذلك لا نعد المستخدم بأن فيديو يوم كامل سيتحلل سريعًا أو أن نفس الخادم يستطيع معالجة كاميرتين مباشرة. يلزم تحسين النموذج ومسار التنفيذ واختيار جهاز edge بناءً على benchmark فعلي؛ مساحة تخزين كافية لا تعالج بطء النموذج.

ذاكرة TensorFlow المقاسة بقيت ٣٨٧ Tensor وقرابة ٣٢MB بيانات نماذج قبل العينات وبعدها. WebGL حجز قرابة ٢٥٠MB مخازن بعد القياس؛ JavaScript heap قرابة ٥٤MB WebGL و٨٨MB CPU. هذه ليست ذاكرة كل عمليات Chromium ولا دليل غياب تسرب عبر يوم كامل. تحميل النماذج والإحماء كان قرابة ٢٫٦s CPU و٥٫٥s WebGL محليًا؛ التحميل الأول من شبكة هاتف مختلف.

| قاعدة مؤقتة، ٢٠ صنفًا، ٥٠٠٠ حدث/يوم | حجم SQLite بعد checkpoint، بلا صور | RSS عملية Node عند القراءة | مطابقة يوم، متوسط / p95 | تقرير يوم، متوسط / p95 |
|---|---:|---:|---:|---:|
| ١٠٠٬٠٠٠ حدث /٢٠ يومًا | ١٦٫٠MB | ١٠٥٫٢MB | ٥٫٣١ /٦٫٣١ms | ٨٫٣٧ /١١٫٣٣ms |
| ١٬٠٠٠٬٠٠٠ حدث /٢٠٠ يوم | ١٦٠٫٦MB | ١٢٤٫٩MB | ٤٫٢١ /٤٫٣١ms | ٦٫٧٣ /٧٫١٦ms |

المقارنة تستخدم API الحقيقي عبر localhost وقراءات cache دافئة، وأُعيدت بعد إضافة الصلاحيات وعرض الأحداث المصححة/المستبعدة. لا تحتوي fixture نفسها تصحيحات. مليون حدث بلا صور أُدخل مباشرة بمعاملة batches، لا عبر HTTP؛ ١٠٠ ألف استغرق نحو ٠٫٣٤s ثم ٩٠٠ ألف إضافية نحو ٣٫٠٤s. لا تستنتج من ذلك قدرة ingest عن بعد أو سرعة رفع مليون صورة. اختبار التقرير تحقق من إجمالي ٥٠٠٠ وإرجاع آخر ١٠٠٠؛ اختُبرت المطابقة على حدود يوم القاهرة. القراءة الأسرع قليلًا بعد مليون صف ناتجة عن عينات قصيرة وcache، ولا تعني أن البيانات الأكبر أسرع بطبيعتها.

هذا baseline قيس قبل أعمدة الصورة/الكتالوج الجديدة وفصل media؛ حجم metadata وزمن القراءة قد يتغيران. لم يُقَس تخزين مليون صورة أو سرعة مخزن الصور أو encryption أو backup أو workload متعدد العملاء. لا نستخدم الرقم القديم كأنه benchmark الإصدار الجديد بالكامل.

## فيديو يوم كامل: عدد الإطارات والزمن

| طول الفيديو لكل كاميرا | إطار كل ٠٫٢ ثانية | كاميرتان | طبيعة الرقم |
|---|---:|---:|---|
| ١٢ ساعة | ٢١٦٬٠٠٠ إطار | ٤٣٢٬٠٠٠ إطار | حساب، لم نحلل هذه المدة كاملة |
| ٢٤ ساعة | ٤٣٢٬٠٠٠ إطار | ٨٦٤٬٠٠٠ إطار | حساب، لم نحلل هذه المدة كاملة |

إذا كان زمن كشف الإطار وتصنيف أربع قصاصات `L` ثانية، فالزمن النظري لمعالجة فيديو واحد طوله `H` ساعة هو `H × 5 × L` ساعة، قبل فك الفيديو والكتابة. مثال حسابي: عند `L=0.1` تكون ٢٤ ساعة نحو ١٢ ساعة معالجة؛ عند `L=0.3` تصبح نحو ٣٦ ساعة. هذه أمثلة وليست قياسات جهازك. معالجة كاميرتين على عامل تسلسلي تضاعف الطلب: هدف ٥fps لكل كاميرا يحتاج ١٠ تحليلات/ثانية وهامشًا للذروة، لا يجوز حساب أداء كاميرا واحدة ثم وعد كاميرتين بالمعدل نفسه.

| استقراء من المتوسط المقاس، أربع قصاصات في كل إطار | فيديو كاميرا واحدة ١٢ ساعة | فيديو كاميرا واحدة ٢٤ ساعة | فيديو كاميرتين ٢٤ ساعة على عامل تسلسلي |
|---|---:|---:|---:|
| CPU الحالي | نحو ٢٧٩ ساعة معالجة | نحو ٥٥٧ ساعة معالجة | نحو ١١١٤ ساعة معالجة |
| WebGL البرمجي الحالي | نحو ٩٢ ساعة معالجة | نحو ١٨٤ ساعة معالجة | نحو ٣٦٧ ساعة معالجة |

هذا **استقراء حسابي ولم ننفذ هذه الساعات**، يفترض دائمًا أربعة تصنيفات لكل إطار، ويفتقد تكلفة seek/decode وبقية التطبيق؛ المشاهد الفارغة قد تحتاج كشفًا فقط، لكن الكشف نفسه بطيء حاليًا. الاستمرار بهذا النموذج في برنامج المتصفح هو تجربة وظائف ودقة على مقاطع قصيرة، وليس توصية إنتاج لمعالجة يوم كامل. يمكن لاحقًا اختبار منطقة خروج محدودة، اختيار إطارات حسب النشاط، نموذج مخصص أسرع، تنفيذ edge محسن وتسريع فعلي؛ كل تحسين يحتاج إعادة قياس الدقة حتى لا نفقد مرورًا سريعًا.

عند الاختبار الطويل نقيس سرعة المعالجة، تأخر آخر إطار، ذاكرة البداية والنهاية، CPU وحرارته، أخطاء فك الفيديو، فقد الهوية بعد الانقطاع، وحجم السجلات والمعلّق منها. نبدأ بمقطع قصير معلّم، ثم ساعة، ثم وردية تشغيل، ثم ٢٤ ساعة على الجهاز المستهدف. الملف المحلي لا يحفظ على الخادم؛ بعد إغلاق الصفحة يلزم اختيار الملف مجددًا. عدم اكتمال التجربة أو عدم حفظ الأحداث يعني نتيجة جزئية، وليس صفر خروج. دقة العد والتصنيف تُقاس منفصلة عن السرعة.

## التخزين: التسجيل الكامل منفصل عن أحداث العد

الحسابات التالية تستخدم GB عشريًا (`10^9` بايت) وMbps عشريًا. السعة المعلنة للقرص ليست المساحة المتاحة بعد التهيئة. المعدلات أمثلة تصميم؛ معدل Hikvision الفعلي يعتمد على الترميز والدقة وFPS وVBR والإضاءة والحركة. قِس الملفات الفعلية لمدة ساعة في وقت الذروة.

`الفيديو GB/يوم = عدد الكاميرات × Mbps × 10^6 ÷ 8 × ساعات التشغيل × 3600 ÷ 10^9`

| كاميرتان؛ معدل كل كاميرا | ساعات/يوم | فيديو GB/يوم | ٣٠ يوم GB | ٣٠ يوم +٢٥٪ هامش GB |
|---|---:|---:|---:|---:|
| ١ Mbps | ١٢ | ١٠٫٨ | ٣٢٤ | ٤٠٥ |
| ٢ Mbps | ١٢ | ٢١٫٦ | ٦٤٨ | ٨١٠ |
| ٤ Mbps | ١٢ | ٤٣٫٢ | ١٢٩٦ | ١٦٢٠ |
| ١ Mbps | ٢٤ | ٢١٫٦ | ٦٤٨ | ٨١٠ |
| ٢ Mbps | ٢٤ | ٤٣٫٢ | ١٢٩٦ | ١٦٢٠ |
| ٤ Mbps | ٢٤ | ٨٦٫٤ | ٢٥٩٢ | ٣٢٤٠ |

هذه مساحة تسجيل NVR/مخزن الفيديو، لا حجم قاعدة بيانات الموقع. تشغيل كاميرتين ٢Mbps طوال اليوم يحتاج قرابة ١٫٣TB فيديو لثلاثين يومًا قبل الهامش، لذلك قرص ٢TB قد يكون بداية مناسبة لهذا السيناريو وحده بعد قياس الواقع؛ عند ٤Mbps طوال اليوم نحتاج أكثر من ٣٫٢TB بعد الهامش، فنختبر قرص ٤TB أو أعلى. مساحة النظام والأحداث والنسخ الاحتياطي والتسجيل الصوتي إن وجد إضافية. لا يسجل التطبيق الحالي الفيديو المتصل.

| أحداث/يوم للمطعم كله | متوسط لقطة KB | لقطات GB/يوم | لقطات ٣٠ يوم GB | لقطات ٣٠ يوم +٢٥٪ GB |

| ٥٠٠٠ | ٨٠ | ٠٫٤ | ١٢ | ١٥ |

أحجام اللقطات **افتراضات** وليست نتائج قياس JPEG مطعم. احفظ الحجم الفعلي عند الاختبار. اللقطات والصور المرجعية أصبحت ملفات في مخزن قرص خاص منفصل عن SQLite؛ keys/bصمات المحتوى metadata في القاعدة. أضف الصور المرجعية والفهارس وسجل المراجعة وملفات WAL/SHM والنسخ الاحتياطي. لا تكفي زيادة ٢٥٪ لنسخة كاملة ثانية: نسخة واحدة متسقة من DB+media تحتاج تقريبًا حجمًا إضافيًا مماثلًا؛ النسخ اليومية الكاملة لثلاثين يومًا قد تضاعف الحجم ثلاثين مرة، فحدّد سياسة احتفاظ ونسخ تزايدية مع تجربة استعادة. مخزن S3 خاص adapter مستقبلي، لا capability موجودة بمجرد فصل الصور.

بيانات الأحداث والفهارس دون الصور في fixture القديمة بلغت نحو ١٦٠ بايت/حدث؛ عند ٥٠٠٠ حدث يوميًا تعادل حوالي ٠٫٨MB/يوم أو ٢٤MB/٣٠ يومًا **لهذه البيانات الاصطناعية قبل أعمدة التخزين الجديدة فقط**. مفاتيح/بصمات الصور والنصوص والتصحيحات وسجل المراجعة تغير الحجم. WAL كان صفرًا بعد checkpoint متعمد؛ لا تعتبر ذلك أن WAL لن ينمو في التشغيل. احتفظ بهامش مساحة عند معاملات الصور والنسخ الطويلة، وأوقف الإدخال بأمان وتنبيه واضح إذا امتلأ القرص. ترحيل BLOB يزيل البيانات داخل الصف بعد التحقق، لكنه لا يصغّر ملف DB فعليًا تلقائيًا؛ offline VACUUM مخطط بعد نسخة آمنة قد يعيد المساحة للنظام.

إذا حدث ٥٠٠٠ حدث يوميًا ومتوسط اللقطة ٨٠KB فإرسال الأحداث يستهلك تقريبًا ٤٠٠MB/يوم قبل overhead، بدل رفع ٤٣٫٢GB/يوم من الفيديو عند ٢Mbps وكاميرتين طوال اليوم. الشبكة الداخلية تحتاج استقبال بث الكاميرتين مع هامش ونقل NVR. رفع الفيديو للسحابة يزيد الحاجة للإنترنت والتكلفة؛ لذلك تحليل edge مع رفع الأحداث واللقطات هو المرشح الأول.

## الأجهزة والخادم: نقطة بداية للاختبار

| المكوّن | اقتراح أولي | الغرض وحدود الاقتراح |
|---|---|---|
| كل نقطة خروج | كاميرا IP ثابتة تدعم RTSP موثقًا، ترميز H.264 متاح، إضاءة ثابتة، PoE عند الإمكان | اختبار زاوية علوية/مائلة تظهر أربعة عناصر؛ تفاصيل الأطباق تحدد العدسة والدقة وFPS، ولا نختار موديلًا نهائيًا قبل التجربة |
| جهاز داخل المطعم لكاميرتين | معالج حديث ٤–٨ أنوية، RAM ‏١٦GB، SSD ‏٥١٢GB، LAN سلكي | مواصفات مرشحة للتجربة؛ لا تثبت قدرة النموذج النهائي على ١٠fps أو ٢٤ ساعة؛ فيديو NVR المستمر له أقراص منفصلة |
| GPU | اختياري حسب القياس، لا شراء قبل النموذج | GPU فعلي وتسريع inference موثوق قد يقللان التأخر؛ WebGL البرمجي داخل بيئة سحابية ليس دليلًا على أداء NVIDIA أو Intel في المطعم |
| خادم ويب تجريبي لموقع واحد | ٢ vCPU، RAM ‏٤GB، SSD دائم ‏٤٠–٨٠GB، HTTPS ونسخ خارج الجهاز | يدير المستخدمين والتقارير والصور؛ التحليل الحالي في المتصفح. هذه توصية بدء لا نتيجة load test؛ راقب CPU/RAM ومساحة الصور والتزامن |
| خادم ويب تجريبي لعدة عملاء | ٤ vCPU، RAM ‏٨GB، DB+media على تخزين دائم مستقل | توصية بدء تحتاج اختبار تزامن وحدود تحميل الصور والحصص؛ ليست شهادة عدد عملاء |
| cloud inference worker | CPU ‏٤–٨vCPU وRAM ‏١٦–٣٢GB وGPU ‏١٦GB مثل T4 مرشح للاختبار | runtime وRTSP/CUDA غير منفذة؛ يجب benchmark هدف كاميرتين ×٥fps =١٠fps وأربع قصاصات وهامش، لا وعد أداء |
| خدمة عدة عملاء | PostgreSQL مُدار أو خادم مخصص + تخزين صور خاص + عمال مهام | تعتمد السعة على العملاء والكاميرات والاحتفاظ والمزامنة؛ SQLite الحالي خدمة واحدة على قرص محلي وليس قاعدة مشتركة لعدة replicas |

لا ترفع دقة التحليل لمجرد رفع دقة التسجيل: يمكن تسجيل فيديو عالي الدقة وتحليل إطار أصغر بعد قياس وضوح الصنف. لا تخفض FPS قبل قياس أسرع مرور؛ يجب أن يبقى العنصر واضحًا عبر عدد كافٍ من الإطارات قبل عبور الخط. المثال الحالي يحتاج استقرار التصنيف أثناء التتبع، ولذلك مرور سريع أو أربع أطباق متداخلة قد يفوّت العد رغم وجود CPU سريع.

## الكهرباء والانقطاع والتعافي

1. UPS يشمل الكاميرات/PoE switch وNVR وجهاز edge والراوتر الضروري، لا الكمبيوتر وحده. نختبر حملًا حقيقيًا وزمن البطارية والإغلاق الآمن. تقدير أولي: `Wh المطلوب ≈ W الحمل × ساعات الاستمرار ÷ الكفاءة`؛ مثل ١٠٠W لمدة نصف ساعة وكفاءة ٨٠٪ يحتاج نحو ٦٢٫٥Wh قبل هامش تقادم البطارية، ولا يُستبدل بهذا القياس تصنيف VA وحده.
2. قبل الإرسال يكتب جهاز edge الحدث على قرص محلي؛ المزامنة idempotent. وقت الحدث يأتي من المصدر المتزامن مع NTP، ووقت الاستلام منفصل. لا تعتمد على الساعة غير المضبوطة بالموبايل للمطابقة النهائية.
3. الخدمة تبدأ مع النظام، تعيد اتصال RTSP بتأخير متدرج، وتراقب وصول **إطارات جديدة** وتغير timestamp لا مجرد استجابة الشبكة. إعادة تشغيل خادم الويب وحده لا تعيد تصوير المتصفح تلقائيًا.
4. بعد التعافي، إن كان NVR سجل الفترة، نعيد تحليلها بمفاتيح كاميرا/زمن وتغطية overlap مراجعة لمنع التكرار. إذا لم تسجل فلا توجد طريقة لاستنتاج جميع الأطباق التي خرجت؛ تسجل فجوة واضحة ويظل تقرير اليوم غير حاسم.
5. الإنذار يحتاج جهة مسؤولة ووسيلة متابعة ومدة استجابة. تحديث واجهة مفتوحة ليس إخطارًا خارجيًا؛ إرسال إشعارات بريد/SMS/WhatsApp يحتاج تكاملًا وصلاحية وإعدادًا منفصلًا.
6. نسخ يومي متسق لـDB+media خارج الجهاز، manifest وبصمات صور، اختبار استعادة وقراءات مخولة، مساحة حرة وتنبيه قرص، سياسة احتفاظ وتشفير أقراص ونسخ وتحديثات. online backup لـSQLite لا ينسخ الصور؛ أوقف الكتابة لنسخ التخزينين أو استخدم snapshot متناسقًا مثبتًا، ولا تنسخ main DB وحده أثناء WAL.

## المطابقة مع الكاشير والواقع التشغيلي

الكاميرا تعد **خروج عناصر مرئية**؛ الكاشير يسجل **طلبات ومبيعات**، والجرد يسجل **استهلاك خامات**. ليست هذه مصادر متطابقة. فرق يومي مفيد لبدء المراجعة، ولا يحدد وحده سرقة أو اسم مسؤول.

| حالة تشغيل | طريقة المقارنة المطلوبة |
|---|---|
| وجبة كومبو بها طبق ومشروب | خريطة SKU الكاشير → أصناف مرئية وكميات كل مكوّن؛ لا نعد الكومبو وعناصره معًا |
| طبق يحتوي حصتين/أحجام مختلفة | وحدة القياس واضحة: طبق أم حصة أم كوب؛ كود لكل اختلاف مؤثر، والتحقق من إمكانية تمييزه بصريًا |
| صينية عليها أربعة أطباق | عد كل عنصر إذا ظاهر؛ الصينية نفسها ليست صنفًا خامسًا. اختلاف الحجب يُختبر، وقد يلزم زاوية ثانية |
| أكواب مغلقة متطابقة | الصورة قد تعرف «كوب» فقط؛ نوع المشروب يحتاج إشارة ظاهرة أو ربط محطة التحضير/الطلب، ولا يُستنتج محتوى لا يظهر |
| إلغاء قبل الخروج | يخصم من الإجمالي المتوقع، مع حفظ حالة الطلب وتوقيتها |
| إلغاء/استرداد بعد الخروج | لا يمحو حدث خروج حقيقي؛ تصنيف استثناء مستقل ومراجعة سبب الإلغاء |
| مجاني، طعام موظفين، إعادة تصنيع، هالك | أكواد أسباب وموافقة حسب سياسة العميل؛ احتساب ما خرج عبر المنطقة، والهالك داخل المطبخ موضوع جرد مختلف |
| طبق عاد ثم خرج مجددًا | قواعد عودة وإعادة تقديم تحفظ الحدثين والعلاقة؛ لا نفترض أنه بيع جديد أو نمحو المرجع الأصلي |
| طلب قبل منتصف الليل خرج بعده | نافذة مطابقة حسب توقيت الطلب والخروج ويوم العمل، لا مقارنة تاريخين جامدين |
| وردية تنتهي ٤ صباحًا | مثال يوم عمل `[04:00,04:00)` بتوقيت المطعم؛ يحتاج إعدادًا واختبارًا لتغير التوقيت الصيفي. لا تعتبر كل صفحة بتاريخ تقويمي دعمًا لهذه الوردية |
| خروج بدون تسجيل كاشير | حالة «مرصود أكثر من المتوقع» تُراجع مع الفيديو والطلبات والاستثناءات، لا حكم آلي بسرقة |
| كاشير مسجل بدون خروج مرصود | تأخير، حجب، توقف تصوير، إلغاء، أو خطأ نموذج من الأسباب الممكنة؛ سجل تحقيقًا ولا تختلق حدثًا |

أفضل تكامل يبدأ بتصدير الكاشير المتاح أو read-only API: رقم مطعم، order ID ثابت، line ID ثابت، SKU، الكمية والوحدة، وقت الإنشاء والتحضير والخروج/الإلغاء، الحالة والتعديلات، وأسباب المجاني والهالك. لا نحتاج أرقام بطاقات أو بيانات دفع حساسة. نخزن هوية المصدر لمنع تكرار الواردات، ونراجع خريطة الأصناف قبل اعتمادها. نقل بيانات CSV يومية الحالية ليس تكامل طلبات آليًا.

صلاحيات التشغيل النهائية تفصل الإدخال والمراجعة واعتماد التصحيحات والإدارة. الكاشير لا يعدل سجل تصوير ليطابق رقمه؛ المدير يراجع فروقًا وأسبابًا، والمراجع يرى الأصل والتعديل وصاحبه وتوقيته. مراقبة موظفين وتقارير خسائر تتطلب سياسة عميل واضحة بشأن الوصول والاحتفاظ بالصور والخصوصية. ابدأ بحسابات محدودة وفصل العملاء، واختبر كل صلاحية على API مباشرة، لا على إخفاء الأزرار فقط.

أدوار النسخة الحالية تحقق هذا الفصل على مستوى وظائفها: المالك ومدير المطعم يديران المراجعة والاعتماد، مسؤول الإدخال يدخل بيانات اليوم ويسجل تعويضًا يدويًا عند الحاجة، المهندس يدير المراجع والتجارب والربط المسموح، والمشاهد يقرأ فقط. اعتماد يوم لا يلغي `complete:false`؛ يحتاج أحدث POS revision وإقرارًا بالتغطية الناقصة. بيانات POS المعتمدة لا تعدل قبل إعادة فتح المدير؛ ظهور أحداث/مجهول أو تصحيح لاحق يفرض إعادة مراجعة. الأرشفة تحفظ IDs وتاريخ العد والمبيعات، والتقارير تتبع تصحيحات موثقة مع حفظ الأصل. سجل التدقيق داخل SQLite ليس حماية من شخص يمتلك تعديل ملف قاعدة البيانات مباشرة.

## بوابات قبول قبل التركيب التجاري

| البوابة | دليل القبول المطلوب |
|---|---|
| الأطباق والمشروبات | فيديو مستقل مع عد وتصنيف بشريين: ١/٢/٤ عناصر، أيدٍ وصوانٍ وتداخل وسرعة وإضاءة وعودة؛ حدود مكتوبة للفقد والتكرار وخطأ التصنيف والمجهول |
| تشغيل الوردية | تنفيذ فعلي على الجهاز المستهدف باثنين stream وقياس التأخر والحرارة والذاكرة، لا ضرب متوسط زمن قصير فقط |
| الانقطاع | فصل إنترنت وكاميرا وكهرباء بصورة مضبوطة؛ لا فقد أحداث محفوظة، فجوات معروضة، اختبار NVR backfill عندما ينفذ، وعدم تكرار بعد التعافي |
| المطابقة | عينات كاشير حقيقية واختبار كومبو وإلغاء بعد خروج وعودة ومجاني ووردية تعبر منتصف الليل؛ لا فروق وهمية بسبب الوحدة أو التاريخ |
| حماية ومراجعة | اختبار أدوار ومنع وصول عميل لآخر، أصل الأحداث وتصحيح موثق، مراجعة حالات غير معروفة، واستعادة نسخة احتياطية ناجحة |

لا نعتمد التقرير النهائي إذا كانت التغطية ناقصة أو الحالات غير المحسومة أعلى من الحد المتفق عليه. نتائج التجارب منفصلة عن التشغيل والمبيعات؛ نحتفظ بإصدار النموذج وإعدادات العد ومراجع الاختبار حتى نقارن التعديلات دون تلويث إجمالي المطعم.
