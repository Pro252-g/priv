# IEP v0.4 — السعة والأجهزة وواقع تشغيل المطعم

تحديث 2026-10-09. حالة الإصلاحات والاختبارات في [مراجعة المشروع](PROJECT_REVIEW.md)، والخطوات الفعلية للتركيب في [دليل التنفيذ](EXECUTION_GUIDE.md). هذه وثيقة حساب وقرار شراء؛ لم يُنفذ تشغيل مطعم فعلي لمدة 24 ساعة أو اختبار دقة على بيانات العميل.

## البنية المعتمدة للتجربة

لكل نقطة خروج كاميرا ثابتة، وجهاز معالجة داخل المطعم، و NVR يحتفظ بالفيديو الأصلي. جهاز المعالجة يرسل **النتائج وقصاصات الأحداث** إلى خادم HTTPS للتقارير والمراجعة والكاشير؛ لا يرفع تسجيل اليوم كله ولا يكرر تخزينه. نفترض شباك أطباق بعرض يقارب مترًا، وأربعة عناصر متزامنة كحد تشغيلي، ونقطة مشروبات مشابهة. زاوية الكاميرا والحجب وسرعة المرور تحتاج قياسًا قبل اعتماد كاميرا واحدة لكل نقطة.

| المسار المنفذ | مكان التنفيذ | حد الاستخدام الحالي |
|---|---|---|
| كاميرا الموبايل، فيديو وصورة محلية | المتصفح، TensorFlow.js | تجربة وظائف وصور ومقاطع قصيرة؛ قفل الشاشة والحرارة والخلفية قد توقفه |
| RTSP و USB وفيديو ملف | عامل Python/OpenCV و ONNX Runtime CPU داخل المطعم | خدمة مستقلة، طابور SQLite، إعادة اتصال، تشخيص ومراقبة؛ قبول جهاز المطعم مستقبلي |
| الويب والتقارير و API | Node 24 و SQLite وصور خاصة على قرص دائم | خدمة واحدة، عزل أدوار ومطاعم ومراجعات؛ ليس PostgreSQL أو مخزن S3 مفعلًا |
| حفظ الفيديو الأصلي | NVR خارج التطبيق | الاحتفاظ حسب الجهاز والأقراص والإعدادات؛ لا استرجاع آلي لأرشيف NVR في التطبيق |

العامل الأصلي يستخدم كاشف YOLOX-tiny وميزات MobileNet-v2 (1280 feature) عند الحاجة للمراجع. نماذج المتصفح مختلفة؛ لا تنقل vectors أو threshold باعتبارها مكافئة بين المسارين. إعادة حساب المراجع ومعايرة كل model profile مطلوبة. قائمة الفئات العامة محدودة، والمراجع لا تدرب كاشف أطباق خاصًا ولا تكشف شيئًا أخفق الكاشف في رؤيته.

## قياس المسار الأصلي الجديد

الدليل المحفوظ: [edge-capacity-2026-10-09.json](review-evidence/edge-capacity-2026-10-09.json). القياس على Linux/Python3.12.14، خمسة CPU ظاهرة وحصة cgroup تعادل **أربعة CPU مشتركة** في بيئة التطوير، وليس على Intel N100 أو i5 أو GPU.

كل عينة تشمل إطار 640×360 حقيقيًا عامًا، YOLOX-tiny، أربع قصاصات مفروضة بميزات 1280، مقارنة 60 vector مخزنًا، التتبع وترميز أربعة JPEG.20 عينة لكل عامل بعد الإحماء. تظهر صورة عامة بها سيارة ودراجة وكلب؛ ليست صورة أطباق أو dataset مطعم.

| المسار | المتوسط ms | p95 ms | أقصى عينة ms |
|---|---:|---:|---:|
| عامل CPU واحد |114.56|159.35|210.63|
| عاملان متزامنان، الأول |147.27|189.54|209.45|
| عاملان متزامنان، الثاني |163.41|228.12|230.31|

هذه نتيجة أفضل لمسار native CPU من baseline المتصفح، وتبرر تجربة الجهاز المقترح. لكنها **لا تشمل** RTSP أو فك الفيديو أو disk queue أو HTTPS أو ضغط وردية أو حرارة الجهاز. p95 للعامل الثاني أكبر من فترة 200ms المطلوبة لخمسة إطارات/ثانية؛ المتوسط وحده لا يضمن عدم إسقاط إطارات. لا نعتمد هدف كاميرتين×5fps قبل قياس المسار الكامل معًا على الجهاز الفعلي. لا تشمل العينة دقة كشف طبق، وتصنيف اسم، أو منع تكرار العودة بعد اختفاء طويل.

إعادة القياس بالأداة `scripts/benchmark-edge.py` موضحة ضمن [دليل التنفيذ](EXECUTION_GUIDE.md)، مع إعداد النماذج والتحقق من بصماتها. استخدم إطارات المطعم المعلّمة، وقِس زمن كل مرحلة و fps الفعلي وعمر أحدث إطار والمفقود من buffer، لا inference وحده.

## قياسات المتصفح وقاعدة البيانات السابقة

[capacity-2026-10-09.json](review-evidence/capacity-2026-10-09.json) baseline تاريخي على نفس بيئة التطوير، Node 24.19.0 و TensorFlow.js، خمس عينات بعد الإحماء. WebGL كان **SwiftShader برمجيًا** بلا GPU فعلي. الكشف وأربع MobileNet قصاصات استغرقا متوسط 4643ms على CPU و 1531ms على SwiftShader؛ هذا المسار لا يحقق 5fps هناك. النتائج لا تمثل سرعة Android أو جهاز edge الجديد.

| SQLite مؤقتة، بلا صور أحداث | حجم DB بعد checkpoint | مطابقة يوم، متوسط | تقرير يوم، متوسط |
|---|---:|---:|---:|
|100 ألف حدث،5000 يوميًا |16.0MB|5.31ms|8.37ms|
|مليون حدث،5000 يوميًا |160.6MB|4.21ms|6.73ms|

هذه قراءات API حقيقية على localhost و cache دافئة قبل أعمدة التخزين والهوية الجديدة؛ ليست load test لعدة عملاء أو مليون صورة. قوائم التقرير تدعم cursor، والإجمالي يغطي الفترة كاملة مستقلاً عن الصفحة. لا نعد أن الإصدار الحالي يحتفظ بحجم 160 بايت/حدث؛ image keys و provenance والتدقيق والتصحيحات تغير الحجم. كرر `npm run bench:capacity` على إصدار النشر وجهازه، ولا تخلط سرعة SQL مع سرعة التعرف.

## فيديو يوم كامل وحدود الوقت

| المدة لكل كاميرا | عينات عند 5fps | كاميرتان |
|---|---:|---:|
|12 ساعة|216,000|432,000|
|24 ساعة|432,000|864,000|

في ملف مسجل، كل 0.2 ثانية من **زمن الفيديو** تعني هدف 5fps، وليس قدرة معالجة فورية. عامل الملفات يربط الأحداث بزمن البداية المعلن و PTS ويعزلها كتجربة؛ إعادة اختيار ملف ليست backfill تلقائيًا للتشغيل.

للتخطيط فقط: زمن معالجة كاميرا واحدة ≈ `ساعات الفيديو ×5×زمن الإطار المركب بالثواني`. عند 0.115 ثانية،24 ساعة تعطي نحو 13.8 ساعة حسابية على عامل تسلسلي، قبل فك/كتابة/شبكة. هذه ليست مدة اختبار منفذ أو وعد بإنهاء يوم. كاميرتان تحتاجان مجموع 10 تحليلات/ثانية مع هامش ذروة؛ المتوازي يقاس معًا لأنهما يتقاسمان CPU والقرص والحرارة.

ابدأ بمقطع مستقل مع عد بشري، ثم ساعة، ثم وردية، ثم 24 ساعة. قِس الدقة، المفقود والمكرر والمجهول، التأخر و fps، حرارة CPU وذاكرة البداية والنهاية، حجم الطابور، فشل الترميز والرفع، والعودة بعد الانقطاع. نتيجة جزئية أو غياب أحداث لا تعني صفر خروج.

## مساحة الفيديو تخص NVR

كل الأرقام التالية GB عشريًا و Mbps عشريًا. المعدل الفعلي يعتمد على H.264/H.265 و VBR والإضاءة والحركة؛ قِس تسجيل ساعة ذروة.

`GB/يوم = عدد الكاميرات ×Mbps×10^6÷8×ساعات التشغيل×3600÷10^9`

| كاميرتان، معدل كل واحدة | ساعات يوميًا | فيديو GB/يوم |30 يوم GB |30 يوم مع 25% هامش GB |
|---|---:|---:|---:|---:|
|1Mbps|12|10.8|324|405|
|2Mbps|12|21.6|648|810|
|2Mbps|24|43.2|1296|1620|
|4Mbps|24|86.4|2592|3240|

هذه سعة أقراص NVR **ولا تضاف تلقائيًا إلى مساحة الكلود**.2TB قد يناسب المثال 2Mbps/24 ساعة بعد قياس التسجيل؛4TB أو أكبر قد يلزم المثال 4Mbps، مع احتساب كاميرات NVR الأخرى والهامش. لا يثبت مجرد وجود القرص نجاح الاحتفاظ؛ راجع أقدم وأحدث وقت قابلين للتشغيل كل يوم.

## مساحة الصور والبيانات والطابور

| أحداث يوميًا للمطعم كله | متوسط اللقطة KB | الصور GB/يوم |30 يوم GB |مع 25% هامش GB |
|---:|---:|---:|---:|---:|
|2000|30|0.06|1.8|2.25|
|2000|80|0.16|4.8|6|
|5000|30|0.15|4.5|5.625|
|5000|80|0.4|12|15|

5000×80KB يعني **12GB صور خلال 30 يومًا** قبل DB والمراجع والنسخ. حجم 80KB افتراض، لا متوسط مطعم مقاس. base64 في طابور الإرسال يزيد البايتات نحو الثلث، مع JSON و provenance؛ لا تستخدم 12GB كحجم outbox. لا يوجد حذف آلي حسب مدة الاحتفاظ أو quota متكامل للعملاء. بعد 90 يومًا بنفس الافتراض تصبح الصور 36GB، وبعد سنة 146GB قبل الإضافات. سياسة الاحتفاظ ومتابعة المساحة شرط تشغيل.

الصور في `IEP_MEDIA_DIR` و SQLite في `IEP_DATA_DIR`. مفاتيح المحتوى وبصماته في DB، و GET الصورة مخول. المساران يُرفضان إذا حلا عبر realpath إلى public؛ static لا يتبع رابطًا إلى الملفات الخاصة. المجلدات الخاصة 700 و DB/WAL/SHM والصور والنسخ 600. فهارس image_key تمنع مسح تاريخ الجداول عند تغيير حالة صورة، وقراءة صورة ready لا تكتب تحديثًا زائدًا. استرجاع ملف pending/missing/corrupt يعيد ready بعد SHA صحيح فقط.

طابور المتصفح محدود 1000 سجل أو JSON تقديري 64MiB. طابور العامل الافتراضي محدود 100,000 سجل و 2GiB مع احتياطي قرص 512MiB؛ يمكن ضبطه في إعداد المصدر. عند بلوغ الحد يتوقف التحليل ويسجل تعطلًا بدل حذف أحداث محفوظة. صفوف blocked بسبب خطأ دائم تحتاج إجراء مهندس؛ زيادة القرص وحدها لا تصلح 401/409. buffer الفيديو الحي يحتفظ بالأحدث؛ الإطارات التي لم تعالج تُحسب مفقودة ولا ترفع كأنها تغطية ناجحة.

| REV-09 | فهارس image_key في الجداول الثلاثة، تحديث عند الانتقال فقط؛ EXPLAIN يستخدم الفهرس وGET متكرر لم يغير total_changes |
| REV-13 | أذونات صريحة 700/600 للبيانات والوسائط وDB/WAL/SHM والنسخ، دون تغيير أذونات ancestors المشتركة |
| REV-14 | buffer hash مشترك 1 MiB، تعداد صفوف تدريجي وMap للتحقق بدل البحث التربيعي؛ قياس DB كبير واختبارات استعادة وفشل |

هذه الإصلاحات لا تنفذ تشفير الأقراص أو offsite أو الحذف الآلي؛ تلك إعدادات وبوابات تشغيل باقية كما يلي.

## النسخ واستهلاك الموارد

`npm run backup` يأخذ snapshot SQLite متسقًا وملفات الصور المشار إليها فقط، مع manifest و SHA والتحقق والاستعادة إلى مسارات جديدة. hash يستخدم buffer1MiB مشتركًا ولا يحمل DB كاملًا في RAM؛ تعداد المراجع تدريجي والتحقق ب Map خطي. manifest و Map يظلان يتناسبان مع **عدد الصور**، فلا ندعي ذاكرة ثابتة لملايين المراجع.

اختبار DB بحجم 100,802,560 بايت بلا صور كبيرة سجل محليًا backup+verify≈242ms وذروة RSS≈50,624KiB. هذا اختبار قصير على قرص/cache البيئة، لا RTO لحجم إنتاج أو مليون صورة أو وجهة شبكة. اختُبرت استعادة صورة من حالة pending قبل GET، رفض ملف تالف ونسخة ناقصة ومسار موجود، وتنظيف الوجهة الجديدة عند فشل مسار media منفصل.

نسخة كاملة إضافية تحتاج تقريبًا حجم البيانات والصور مرة أخرى، وليس 25% فقط. النسخ الكاملة اليومية 30 يومًا قد تستهلك أضعافًا كبيرة؛ حدد جدولًا واحتفاظًا ووجهة مشفرة خارج الخادم. Compose يوفر مهمة نسخة على volume محلي؛ لا يجعلها offsite أو مجدولة أو مشفرة تلقائيًا. ترحيل BLOB يحفظ snapshot تمهيديًا ويحقق الصورة قبل تفريغها؛ حجم ملف SQLite لا يصغر تلقائيًا، و VACUUM يحتاج صيانة ونسخة ومساحة إضافية. [التشغيل والاستعادة](OPERATIONS.md) يحدد إجراءات الفشل.

## الكهرباء والانقطاع

UPS يغطي الكاميرات و PoE و NVR والجهاز والشبكة اللازمة. اختبر زمنه بالحمل الفعلي والإغلاق الآمن؛ تقريب Wh = `W×ساعات÷كفاءة` مع هامش عمر البطارية. systemd يشغل العامل مع الإقلاع وإعادة فشله، و Compose يعيد خادم الويب، لكن لا يمكن تسجيل خروج أثناء غياب التصوير.

العامل يحفظ الحدث محليًا قبل إرساله، ويحافظ على هوية إعادة المحاولة، ويرسل health وفجوات. المصدر له هوية ثابتة و producer lease لمنع عوامل متعارضة؛ لا تبدأ عاملين لنفس نقطة العد. وقت RTSP الحالي هو **وقت استلام decoder على جهاز edge بتوقيت UTC**، وليس timestamp من NVR؛ اضبط NTP على الجهاز والكاميرات والكاشير وقِس تأخر البث.

عند الانقطاع راجع الطابور والفجوة وتسجيل NVR. استيراد ملف يدوي كتجربة متاح؛ استرجاع أرشيف NVR وتحويله إلى backfill تشغيلي دون overlap ليست خدمة منفذة. نبضة اتصال ليست إثبات دقة أو اكتمال. لا يوجد تنبيه SMS/بريد تلقائي مكتمل؛ عين مسؤول متابعة ووسيلة خارجية قبل التشغيل التجاري.

## الكاشير والواقع التشغيلي

الكاميرا ترصد خروجًا مرئيًا، والكاشير يسجل طلبًا، والجرد يسجل خامات. فرق العدد يبدأ تحقيقًا؛ لا يثبت سرقة أو اسم مسؤول.

| الحالة | قاعدة المقارنة |
|---|---|
|كومبو طبق ومشروب|خريطة SKU إلى المكونات والكميات؛ لا عد الكومبو ومكوناته معًا|
|صينية بأربعة أطباق|عد الظاهر كلًا على حدة؛ الصينية ليست صنفًا خامسًا|
|أكواب مغلقة متطابقة|«كوب» لا يثبت نوع المشروب؛ يحتاج علامة أو ربط طلب/محطة|
|إلغاء قبل الخروج|يخصم من المتوقع؛ الاسترداد بعد خروج لا يمحو الحدث|
|مجاني أو موظفون أو إعادة تصنيع أو هالك|أسباب وموافقة؛ يدخل المتوقع ما خرج عبر منطقة العد فقط|
|عاد طبق ثم خرج|وثق العلاقة والسبب؛ لا تستنتج أنه بيع جديد|
|طلب قبل منتصف الليل وخرج بعده|راجع توقيت الطلب والخروج؛ اليوم الحالي تقويمي Africa/Cairo مع DST، ووردية 04:00 تحتاج تطويرًا واختبارًا|
|أكثر من المتوقع|راجع الفيديو والطلبات والاستثناءات؛ ليس اتهامًا آليًا|
|أقل من المتوقع|تأخير أو حجب أو انقطاع أو خطأ كشف/تصنيف من الاحتمالات|

POS الحالي إدخال/CSV مع revisions ومعادلة `sold−cancelled+complimentary+waste`، وليس موصلًا آليًا لكل كاشير. أصناف person/object خارج مقارنة المبيعات. ابدأ read-only export أو API للكاشير، مع order/lineID و SKU والكمية والحالة والتوقيت وأسباب الاستثناءات؛ لا بيانات بطاقات. مدير المطعم يعتمد اليومية بعد مراجعة المجهول والفجوات، والمهندس يعالج الربط، ومسؤول اليومية يدخل القيم؛ المراجعة والتصحيح يحفظان الأصل.

2. كاميرتان فعليتان مع fps وتأخر وحرارة وذاكرة وطابور؛ ساعة، وردية، ثم 24 ساعة.
3. فصل إنترنت وكاميرا وكهرباء بصورة مضبوطة؛ بقاء الأحداث المحفوظة، ظهور الفجوة، ومنع التكرار بعد العودة.
4. مطابقة كاشير حقيقية وإلغاء وكومبو ومجاني وحدود اليوم؛ قبول صلاحيات العملاء وصور مخولة.
5. نسخة خارج الخادم واستعادة كاملة على أقراص النشر و RPO/RTO ومسؤول متابعة.

المتوسط المقاس والاختبارات البرمجية لا تغلق هذه البوابات الميدانية. لا يُعتمد تقرير كامل إذا بقيت فجوة أو حالة غير محسومة تتجاوز سياسة المطعم.
