# IEP v0.4 — تشغيل المطعم وتشخيص الربط والمراجعة والتعافي

تحديث 2026-10-09. [دليل التنفيذ](EXECUTION_GUIDE.md) يشرح تركيب Ubuntu و NVR والكاميرات والجهاز والكلود والأوامر. هذه الوثيقة لإدارة اليومية والفشل والاستعادة؛ [مراجعة المشروع](PROJECT_REVIEW.md) مرجع الإصلاحات وحدود الاختبارات.

## ما تعنيه النتيجة

النظام يرصد عنصرًا ظاهرًا، يحاول تعريف صنفه، ويتتبع عبوره منطقة الخروج ثم يحفظ واقعة ولقطة وتوقيتًا. التقرير ليس جرد خامات ولا إثبات سرقة. «مجهول» يعني كشفًا متتبعًا تعذر حسم صنفه؛ شيء لم يكشفه النموذج لا يولد تلقائيًا سجلًا مجهولًا. الأكواب المغلقة المتطابقة قد تظهر ككوب دون معرفة محتواها.

الصورة الثابتة تعطي ملخص محتويات كتجربة منفصلة، ولا تسجل خروج طلب في اليومية. فيديو التجربة وملف العامل الأصلي معزولان عن التشغيل والكاشير. كاميرا المتصفح المتحركة تحتاج تأكيدًا يدويًا؛ العد التلقائي عبر خط يحتاج كاميرا ثابتة ومعايرة ومعدل إطارات كافيًا.

## قبل أول تشغيل

1. سمِّ نقطتي الخروج، ثبّت كاميرا كل نقطة وإضاءتها، واختبر أربعة عناصر والحجب. تأكد أن NVR يسجل أصل الفيديو وراجع أقدم وأحدث تسجيل فعليين.
2. اضبط NTP على edge والكاميرات و NVR والكاشير. وقت RTSP الحالي هو وقت استلام decoder على edge بتوقيت UTC، وليس PTS من NVR؛ قِس التأخر بين التصوير والاستلام.
3. أنشئ مطعمًا وأصنافًا ومراجع وأدوارًا ومصدرًا ثابتًا لكل كاميرا و model profile مناسبًا. لا تعيّن صنفين عامًا للفئة نفسها وتعتبر الاختيار مضمونًا.
4. راجع ROI وخط واتجاه العد، نموذج ONNX وبصمته وعتبات التعرف. النماذج في المتصفح والعامل مختلفة؛ vectors والمعايرة لا تنقل تلقائيًا بينهما. لا تبدأ عدًا تجاريًا قبل الموافقة على المعايرة.
5. جهز مفاتيح API محدودة بالمطعم والنطاقات اللازمة، ومجلدات خاصة و outbox ونسخًا خارج الجهاز، و UPS يغطي التصوير والشبكة والجهاز.
6. نفذ فحص الربط ثم مقطعًا معلّمًا ثم ساعة ووردية و 24 ساعة على الجهاز الفعلي. السرعة والدقة والانقطاع اختبارات منفصلة، ولم تُعتمد نتائج مطعم في هذا العمل.

التطبيق يعرض صلاحيات بحسب الدور، والخادم يفرضها أيضًا. المالك يدير العملاء والمستخدمين، مدير المطعم يراجع ويعتمد، مسؤول اليومية يدخل الكاشير، المهندس يضبط المراجع والتجارب والربط، والمشاهد يقرأ فقط. راجع [المخاطر والصلاحيات](RISK_AND_ACCESS.md) قبل تسليم الحسابات.

## فصل طبقات الربط وتشخيصها

`check` للعامل يفحص التخزين والنماذج و TCP للمصدر و HTTPS والصلاحيات والكتالوج والمعايرة ثم فك إطار و inference. `diagnose` يقرأ health المحلية وعمرها؛ تسجيل نجاح فحص واحد لا يعني استمرار بقية المسار. الأوامر في [دليل التنفيذ](EXECUTION_GUIDE.md).

| العلامة | التفسير الأقرب | الإجراء والتحقق بعد الإصلاح |
|---|---|---|
| الموقع لا يفتح، DNS أو TLS يفشل | نطاق/شهادة/جدار ناري/حاوية proxy | راجع DNS و 80/443 و Compose health وسجلات منقحة؛ لا تفتح Node أو NVR عشوائيًا |
| API يعمل والمصدر لا يصل TCP | IP أو VLAN أو منفذ RTSP أو NVR مغلق | افحص LAN والمسار من edge إلى NVR؛ نجاح ping وحده لا يثبت RTSP |
| TCP يصل لكن لا يوجد إطار | حساب الكاميرا أو channel أو codec أو decoder | افحص المصدر محليًا بأسرار محمية و H.264؛ راجع code `source_unreachable` أو `decoder_unavailable` |
| `auth_failed` أو 401/403 | مفتاح منتهي/ملغى أو نطاق/مطعم غير مسموح | صحح المفتاح محليًا وراجع النطاقات؛ لا تغيّر الهوية لتجاوز الصف المعلق |
| `calibration_required` | profile أو ROI/خط أو بصمة نموذج غير موافق عليها | قارن الإعدادات بسجل المصدر وراجع المعايرة قبل استئناف العد |
| `inference_failed` | ملف/بصمة نموذج أو runtime أو معالجة | افحص model hash و provider وذاكرة الجهاز؛ توقف آمنًا وسجل فترة عدم الثقة |
| `storage_full` | مساحة أو حد outbox | أضف مساحة أو أصلح الرفع بعد نسخة آمنة؛ لا تمسح queue أو media كحل سريع |
| طابور يكبر و HTTPS غير متاح | انقطاع إنترنت أو server | الأحداث المحفوظة تنتظر؛ راقب عمر الأقدم والحدود ثم تحقق من وصولها دون تكرار |
| صفوف blocked أو 409 | خطأ دائم أو هوية/محتوى متعارضان | تحقق من الأصل والمعرفات وحجز المنتج lease وprofile؛ عالج السبب قبل إعادة الصفوف، ولا تولد IDs جديدة لنسخها |
| مصدر running لكن fps منخفض أو frame age كبير | بطء نموذج/فك/CPU/بث | قِس المسار الكامل والمفقود؛ تشغيل العملية لا يثبت تغطية العبور السريع |
| health قديم/offline | الخدمة ماتت أو النبضات لم تصل | قارن health المحلي بالسحابي وحالة systemd والشبكة؛ افتح فجوة للمراجعة |
| صورة pending/missing/corrupt | فشل كتابة أو فقد ملف أو عدم تطابق SHA | أعد payload الأصلي أو استعد media من نسخة صحيحة؛ العدد لا يُرسل بهوية جديدة |

لا تعرض RTSP URL أو API key أو password في screenshots أو logs أو support tickets. بيانات الأسرار في env محمي على الجهاز، وليست في JavaScript أو config العام. المصدر له هوية ثابتة و producer lease؛ لا تشغل عاملين لنفس نقطة الخروج. انتهاء lease أو تعارض منتج يحتاج تحققًا، لا تغيير sourceId لفرض عد ثانٍ.

## الطابور وتوقف التصوير

المتصفح يكتب payload في IndexedDB قبل الإرسال، مرتبطًا بالحساب والمطعم والتجربة، دون بيانات دخول. الإرسال منفصل عن inference ويعيد المحاولة؛ حد 1000 سجل أو 64MiB JSON تقديري. عند الحد تتوقف المعالجة بدل إسقاط القديم. المتصفح ليس خدمة وردية: eviction أو private browsing أو قفل الشاشة أو إغلاقه قد يقطع التصوير، ولا يعوضه restart لخادم الموقع.

العامل الأصلي يحفظ الأحداث في SQLite محلي، مع إعادة إرسال مستقلة و payload ثابت. افتراضيًا 100,000 سجل و 2GiB وطوارئ مساحة 512MiB؛ هذه حدود لا مدة استمرار مضمونة. base64 يضيف مساحة، ولذلك احسب انقطاع الإنترنت بحجم queue الفعلي. استجابة `mediaPending` تبقي طلب الصورة لإعادة المحاولة دون إعادة العد. أخطاء الشبكة تُعاد، والأخطاء الدائمة مثل 401/403/409 تتحول blocked وتحتاج إجراء؛ لا تُعامل كتسليم ناجح.

القراءة الحية تحفظ أحدث إطار ضمن buffer محدود وتراقب المفقود؛ استمرار التتبع لا يعيد إطارًا لم يُعالج. العامل يراقب المصدر والعملية والطابور ويعيد الاتصال ويسجل فجوات؛ pixel fingerprint غير المتغير طويلًا يستدعي عدم ثقة، وقد يكون مشهدًا ساكنًا صحيحًا، وليس تشخيصًا يقينيًا لتجمد NVR. نبضات السحابة قد تنقطع بسبب الإنترنت رغم استمرار الجهاز محليًا؛ راجع الأدلة المحلية.

المراقبة تحفظ الفجوات بعد التعافي، لكن لا تعرف تلقائيًا أن سببها انقطاع كهرباء. تشغيل العامل مع systemd وإعادة فشله لا يسجل وقت غياب الكاميرا. هوية إعادة المحاولة ومنع المعروف/المجهول لنفس واقعة العبور لا يثبتان هوية نفس الطبق بعد حجب طويل أو خروج ثم عودة؛ هذه حالات قبول ميداني.

## تجربة فيديو أو صورة ومراجعة المراجع

اختر المطعم والمراجع ثم ملف JPEG/PNG أو فيديو صغير. أمثلة تقديم الصنف تكون متعددة وحقيقية ومسمّاة؛ `kind` طبق/مشروب/عنصر/شخص وصف كتالوج، وليس تدريبًا. مسار `reference` يقارن الميزات، و`detector` يربط فئة عامة متاحة بالصنف؛ التباس الفئة أو درجات متقاربة ينتج مراجعة بدل اختيار اعتباطي.

في المتصفح، الفيديو يُحلل محليًا ولا يرفع كاملًا. manifest وبصمة الملف والمراجع والإعدادات محفوظة للتجربة، و`mediaTimeSec` موقع الحدث داخل الفيديو؛ وقت التحليل ليس وقت تصويره الحقيقي. إعدادات التشغيل والمراجع لها provenance ثابت؛ تغييرها يستلزم توقفًا/تشغيلًا جديدًا وفق الواجهة. الصورة المحفوظة تُفتح كملخص أصناف، لا كسجل عبور فارغ.

ملف العامل الأصلي يتطلب تجربة معزولة وبصمة ووقت بداية معلنًا، ويستخدم PTS لتوقيت الحدث. لا تستخدمه كتسوية آلية لفجوة live؛ archive backfill يحتاج موصلًا وسياسة overlap غير منفذين. اكتمال قراءة الفيديو لا يثبت وصول الأحداث: راجع outbox والسجل المحفوظ. قارن بمشاهد مستقلة معلّمة بشريًا:1/2/4 عناصر، أيدٍ وصوانٍ وتداخل وسرعة وعودة وإضاءة وانقطاع.

## الكاشير والتصحيحات واعتماد اليوم

CSV أو الحفظ الحالي بديل كامل لأصناف اليوم، مع revisions محفوظة. استخدم dishId عند تكرار الأسماء، وانتظر تحميل المطعم والتاريخ قبل الإدخال. sold إجمالي قبل الإلغاء، cancelled ما أُلغي قبل خروج، complimentary مجاني خرج، waste هالك مر بمنطقة العد. التوقع = `sold−cancelled+complimentary+waste`. لا تخصم استردادًا بعد خروج ولا تضف هالكًا لم يمر بالشباك.

person/object خارج مقارنة المبيعات؛ كوب مغلق أو وعاء عام لا يثبت نوع الطلب. كومبو يحتاج خريطة مكونات ووحدات من الكاشير؛ CSV يومية ليست موصل طلبات آليًا. اليوم الحالي تقويمي Africa/Cairo مع DST، ووردية تبدأ 04:00 ليست إعدادًا مكتملًا. راجع طلبًا قبل منتصف الليل خرج بعده، والعودة والمجاني وإعادة التصنيع والحجب قبل تفسير الفرق.

الأرشفة تحفظ الصنف وتاريخه؛ known events الأصلية لا تُحذف لتساوي الكاشير. المدير يصحح `void` أو `reclassify` بسبب ومستخدم ووقت، ويؤكد مجهولًا أو يستبعده موثقًا. تأكيد مجهول لا يضاعف نفس هوية العبور إذا كانت معروفة، ولا يصبح تعلمًا تلقائيًا ناجحًا. uploads/deletes للمراجع لها تدقيق وبصمة؛ تغيير اسم أو صور يغير نموذج المقارنة ويستدعي مراجعة.

اعتماد اليوم مربوط بأحدث POS revision وإقرار التغطية. اليوم المعتمد يرفض تغيير POS حتى يعاد فتحه؛ أحداث أو مجهول أو تصحيح لاحق يحتاج مراجعة. غياب فجوة heartbeat لا يعني دقة أو اكتمال وردية. سجل التدقيق داخل SQLite لا يحمي من مدير OS يغير قاعدة البيانات مباشرة؛ إجراءات أقوى تحتاج حماية وتشغيلًا إضافيين.

## الكهرباء و NVR والاسترجاع

UPS يشمل الكاميرات/PoE و NVR و edge والراوتر الضروري. اختبر البطارية والحرارة والإغلاق والإقلاع بالحمل الفعلي. إذا انقطع الإنترنت وبقي التصوير والجهاز، يمكن أن يستمر الحفظ المحلي حتى حدود الطابور؛ إذا انقطعت الكهرباء أو التصوير فلا توجد أحداث عن الجزء غير المشاهد.

بعد التعافي، تحقق من الخدمة و health والمعلق والفجوات وتسجيل NVR. تنزيل أرشيف NVR وتحليل فترة الفجوة تلقائيًا وإدخالها كعد تشغيلي دون overlap **غير منفذ**. ملف فيديو يمكن اختباره منفصلًا، أو يراجع المدير الأصل ويضيف تعويضًا يدويًا موثقًا عند سياسة تسمح؛ لا تعلن التقرير كاملًا بمجرد اتصال الجهاز مجددًا.

## أوامر النسخ والتحقق والاستعادة المنفذة

Node 24 مطلوب. حدّد `IEP_DATA_DIR` و`IEP_MEDIA_DIR` المصدرين، ووجهة نسخة جديدة تديرها بصلاحيات مناسبة. الأداة لا تنقل خارج الجهاز أو تشفّر أو تجدول وحدها؛ Compose يحتوي مهمة محلية لنفس العملية، وخطواتها في [دليل التنفيذ](EXECUTION_GUIDE.md).

```sh
npm run backup -- --output /backup/iep-2026-10-09
npm run backup -- --verify /backup/iep-2026-10-09
# الاستعادة إلى مسارين جديدين؛ أوقف الخدمة قبل تبديل إعداداتها إليهما.
npm run backup -- --restore /backup/iep-2026-10-09 --data-dir /restore/iep-data --media-dir /restore/iep-media
```

الأداة تأخذ SQLite online snapshot، ثم الصور المشار إليها في هذه النسخة فقط. تتحقق من الحجم و SHA للملفات و DB و manifest، وتنسخ حصريًا وتتحقق بعد النسخ. hash ب buffer1MiB لا يحمل DB كله؛ manifest و Map يستهلكان ذاكرة بحسب عدد الصور. نقص/تلف صورة يجعل `complete:false` و exit2 في النسخ/التحقق؛ خطأ التحقق exit1. الاستعادة ترفض الناقص افتراضيًا؛ `--allow-incomplete` طوارئ صريحة بعد مراجعة أثر الصور المفقودة، وليس قبولًا تجاريًا.

الاستعادة ترفض وجهة موجودة، وتزيل المخرجات الجديدة عند فشل وجهة media أو النسخ دون الكتابة فوق dataset سابق. الصور الصحيحة تُصبح ready ومراجعها متاحة قبل GET. `pending` لا يشفى من حجم الملف فقط؛ SHA شرط التحقق. فشل حفظ صورة لا يكرر العدد، وإعادة الأصل أو استعادة نسخة الصحيحة تصلح الوسائط.

بعد نجاح الاستعادة: أوقف التطبيق، بدّل **المسارين معًا**، ابدأه، وسجل الدخول وافتح مراجع ولقطات known/unknown وتقريرًا معلومًا واختبر queue. هذا ليس تبديلًا ذريًا عبر قرصين. لا تنسخ main SQLite وحده أثناء WAL وتعتبره backup؛ snapshot DB لا تنسخ media إلا بأداة الزوج أو خطة متناسقة. snapshot ترحيل BLOB تحت `migration-backups` ليست بديلًا لنسخة DB+media خارجية.

المجلدات 700 والملفات 600؛ الصور الخاصة ليست public ولا S3 مفعلًا. ترحيل BLOB يتحقق من البايتات قبل إزالته ويحفظ fallback عند فشل التخزين؛ ملف DB لا يصغر تلقائيًا. VACUUM صيانة مخططة بعد نسخة واستعادة ومساحة إضافية. لا يوجد حذف آلي بحسب المدة؛ راقب نمو الصور والنسخ والتخزين الحر. تشفير القرص والنسخ، و RPO/RTO وجدول واحتفاظ ومسؤول، من إعداد المشغل قبل الإنتاج.

اختُبرت snapshot واستعادة بيانات مؤقتة وصور مخولة، رفض تلف ووجهة موجودة ونسخة ناقصة، إصلاح pending، وفشل media منفصل. اختبر مرة أخرى على volumes الإنتاج ونسخة مشفرة خارج الخادم؛ نجاح ملف محلي ليس اختبار كارثة استضافة.

## الاختبارات وحدود القبول

`npm test` يغطي الخادم والصلاحيات والهوية والتوقيت والتخزين والتتبع. `npm run test:browser` يغطي الواجهة والطابور وحالات السباق والمصدر المتجمد والتجارب؛ fixtures الاصطناعية لا تثبت دقة مطعم. `npm run test:models` يفحص نماذج المتصفح الحقيقية. `npm run test:edge` يغطي العامل والمصدر والطابور والنماذج بحسب fixtures المتاحة. Chromium/Playwright أدوات اختبارات الواجهة، وليسا متطلبات حاوية API؛ العامل له Python/OpenCV/ONNX مستقل.

القياس الأصلي المحدود الجديد ≈114.56ms لعامل و 147.27/163.41ms لعاملين، مع كشف وأربع قصاصات و 60 vector وتتبّع وأربعة JPEG. لا يشمل RTSP/decode/قرص/HTTPS؛ ليس اختبار i5-1235U أو N100 أو 24 ساعة أو دقة أطباق. baseline المتصفح أبطأ ومذكور منفصلًا في [السعة](CAPACITY_AND_OPERATIONS.md). قبل التركيب التجاري يلزم مصدران فعليان، قبول دقة مستقل، وردية ثم 24 ساعة، انقطاع ومزامنة، استعادة وأدوار ومقارنة كاشير.
