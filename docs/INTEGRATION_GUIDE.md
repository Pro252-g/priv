# IEP — شاشة API ومرجع الربط

> تحديث المراجعة 2026-10-09: [التقرير الشامل والأدلة](PROJECT_REVIEW.md) هو مرجع الحالة الحالية؛ يسجل عيوبًا مفتوحة وأولويات إصلاح وخطة قبول. نجاح الاختبارات القائمة لا يغلق الحالات الجديدة.

شاشة **الربط وAPI** تعرض المسارات والصلاحيات، تنزيل OpenAPI، وفحص GET آمن. الإدارة المخولة تنشئ مفتاحًا لنطاقات ومطاعم محددة لمدة ١–٣٦٥ يومًا وتلغيه. قيمة المفتاح تظهر مرة واحدة في حقل مخفي؛ لا تضعها في Git أو سجلات أو متصفح عميل عام. [OpenAPI JSON](openapi.json) نسخة محفوظة، و`GET /api/openapi` المرجع الفعلي بعد الدخول. التفاصيل الإجرائية في [server/API.md](../server/API.md).

## المصادقة والتعاقد

المتصفح يستخدم جلسة HttpOnly/SameSite. الموصل الخادمي يستخدم `Authorization: Bearer <INTEGRATION_KEY>` عبر HTTPS. لا تتصل بالموصل ببيانات دخول موظف. مفتاح POS يحتاج `pos.read,pos.write`، مفتاح كاميرا `catalog.read,events.write,monitor.write,monitor.read` وفق الوظيفة، ومفتاح تقارير `reports.read`. المفتاح لا يمنح أكثر من منشئه ولا يخرج عن مطاعمه؛ المهندس لا ينشئ مفتاح مبيعات. تعديل الدور/المطاعم أو تعطيل الحساب يبطل الجلسات والمفاتيح القديمة نهائيًا. مفاتيح الربط لا تدير الهوية أو اعتماد المدير.

JSON هو تنسيق الإدخال والإخراج، عدا الصور/CSV. أخطاء `{error:string}`: 400 مدخل غير صالح، 401 دخول/مفتاح غير صالح، 403 صلاحية مرفوضة، 404 مورد غير موجود أو خارج النطاق، 409 تعارض مراجعة/يوم معتمد، 413 حجم زائد، 429 عند تجاوز حماية الدخول. لا يُسمح CORS عام. صحة الخادم `GET /api/health` لا تثبت صحة الكاميرا أو دقة الكشف.

## ربط الكاشير

لا يوجد موصل خاص بمورد الكاشير الحالي قبل معرفة اسمه وصيغة تصديره. شاشة **مطابقة المبيعات** تستقبل CSV أو كتابة يدوية. صيغة المثال:

```csv
dishId,sold,cancelled,complimentary,waste
42,100,3,2,1
```

يمكن استخدام `dishName` إذا كان الاسم فريدًا ومطابقًا. يجب أن تشمل شاشة CSV كل الأصناف النشطة مرة واحدة لأن الحفظ استبدال كامل. موصل API يجب أن يرسل snapshot يوم كامل متفق عليه؛ صفوف غائبة ليست توقعًا صفرًا بل بيانات مفقودة. استخدم جدولًا صريحًا `cashierCode → dishId` والوحدة والوصفة: الكومبو يتحول إلى أطباق ومشروبات، عدد الطلبات لا يساوي عدد الأطباق.

```json
{
  "restaurantId": 1,
  "businessDate": "2026-10-09",
  "revision": "cashier-export-day-0001",
  "items": [{"dishId":42,"sold":100,"cancelled":3,"complimentary":2,"waste":1}]
}
```

أرسل إلى `POST /api/pos`. `sold` يشمل إجمالي وحدات الطلب قبل استبعاد الإلغاء الذي لم يخرج؛ `cancelled` فقط وحدات ضمن sold لم تعبر للخارج. `complimentary` و`waste` وحدات إضافية خرجت فعلًا عبر نقطة القياس ولم تدخل sold؛ لا تجمع نفس الوحدة مرتين. المتوقع = sold − cancelled + complimentary + waste. إلغاء بعد خروج طبق لا يُخصم منه، والهالك داخل المطبخ الذي لم يعبر لا يدخل. طبّق تطبيع هذه المعاني في الموصل، لأن حقول API لا تسجل تاريخ الطلب الكامل وأسباب المرتجعات مفصلة.

الكميات أعداد صحيحة ٠–١٬٠٠٠٬٠٠٠، حتى ٥٠٠ صف، والإلغاء ≤ sold. إعادة نفس revision بنفس البيانات آمنة؛ استخدامه لمحتوى مختلف يرجع 409؛ تعديل اليوم يحتاج revision جديدًا. إعادة إصدار قديم لا تجعله الحالي. اليوم المعتمد يحتاج إعادة فتح مخولة قبل التعديل. احفظ كود/نسخة المصدر والتوقيت في سجلات الموصل لتفسير الاختلافات.

`GET /api/reconciliation?restaurantId=1&businessDate=YYYY-MM-DD` يعيد الصفوف والتوقع والمرصود والفارق (مرصود − متوقع)، مراجعة المدير، الجلسات والفجوات والتحذيرات وعدد unknown غير المحسوم. `coverage.complete` يبقى false لأن النبضات لا تثبت الدقة. التاريخ في Africa/Cairo؛ حدود اليوم `[from,to)` تشمل التوقيت الصيفي. وردية تشغيل خاصة تعبر منتصف الليل تحتاج تطوير تعريف يوم موحد بين POS والكاميرا.

## أحداث المعالجة والمصدر

موصل edge المستقبلي يرسل إلى `POST /api/events`؛ الخدمة الحالية تعالج داخل المتصفح. الحدث يحتوي `dishId,sessionId,trackId,crossingId,camera,occurredAt,confidence,mode`؛ الوقت ISO UTC، النوع automatic، والتشابه ٠–١. صورة JPEG/PNG اختيارية حتى ٥١٢KiB لكل حدث، وجسم HTTP حتى ٣MiB؛ لا تجمع ٢٠٠ صورة كبيرة في طلب واحد. ٢٠٠ حدث الحد الأقصى للدفعة.

ثبّت `(sessionId,trackId,crossingId)` **قبل** الإرسال واحفظه محليًا. إعادة الإرسال ترجع `{inserted,duplicates}` ولا تضاعف السجل. التشغيل الجديد يحتاج session جديدًا، والاسترجاع من NVR يحتاج خطة تداخل وهوية أحداث محفوظة؛ تغيير المعرفات عند الإعادة يكرر العد. لا يثبت منع تكرار السجل أن الطبق الفيزيائي لم يعد بعد اختفائه.

العبور غير المؤكد يرسل إلى `POST /api/unknown-events`، بنفس مفاتيح الحدث وreason دون dishId؛ حتى ١٠٠ لكل دفعة وبنفس حدود الصورة والجسم. لا يدخل مجموع صنف حتى حسمه بقرار مدير عبر `/api/unknown-events/{id}/resolve`. قائمة المجهول تعرض أحدث ٢٠٠ سجل للقراءة الحالية؛ ليست تصديرًا لكل التاريخ. تصحيحات `/api/events/{id}/corrections` تسجل void أو reclassify وreason وتحفظ الأصل. هذه قرارات إدارية وليست scopes لمفتاح الكاميرا.

ابدأ `/api/monitor/start` بهوية `sourceId` ثابتة لكل كاميرا، `sessionId` جديد، `camera` اسم العرض وrestaurantId. نبضة `/api/monitor/{id}/heartbeat` كل ١٥ ثانية: `running` فقط عند وجود إطارات ومعالجة حديثة، وإلا `stalled`. ٤٥ ثانية دون نبضة تُنتج فجوة unknown، لا يفترض سبب الكهرباء. انتهاء المصدر `/end` مع reason. جلسة جديدة لنفس sourceId تُحدّد نهاية فجوة الجلسة السابقة. لا تستخدم نفس sourceId لكاميرتين.

بروتوكول Hikvision RTSP/ONVIF وخدمة edge/استرجاع NVR غير منفذة؛ هذه الواجهة تجهز استقبال أحداثها بعد بنائها، ولا تجعل RTSP قابلًا للفتح مباشرة في Android Chrome.

## قراءة تاريخ كبير والتجارب

`GET /api/reports?restaurantId=1&businessDate=YYYY-MM-DD&limit=200` يعيد مجاميع **الفترة كلها** و٢٠٠ حدث مرتبة بوقت الحدث ثم المعرف تنازليًا. كرر نفس الفلاتر مع `beforeOccurredAt` و`beforeId` من `nextCursor` حتى hasMore=false. لا تستخدم المعرف وحده: البيانات المتأخرة قد يكون تاريخها أقدم ومعرفها أحدث. الصفحة التالية ليست snapshot ثابتًا؛ سجلات متأخرة قد تستلزم تحديث الفترة وإزالة تكرار IDs من التصدير. بدون معاملات الصفحات يوجد حد توافق آخر ١٠٠٠ حدث. `reports.csv` يجمع الأصناف، وليس ملف جميع اللقطات.

`fromDate,toDate` أيام شاملة، أو `from,to` أزمنة ISO بحد علوي مستبعد. لا تخلط أنواع الفلاتر في الموصل. `experimentId` يختار تجربة واحدة؛ عدم إضافته يستبعد التجارب من التقارير الحية والمطابقة. الفيديو محلي، ما يخزن على الخادم بيانات التجربة والأحداث واللقطات، وليس الفيديو الكامل.

في تجربة مسجلة يشير `mediaTimeSec` إلى موضع الحدث داخل الفيديو؛ `occurredAt` تاريخ تشغيل التجربة المضاف إليه موضع الإطار، وليس التاريخ الأصلي للتصوير. لا تنقل هذه الأحداث إلى اليومية الحية. البصمة المحفوظة لملف الفيديو مبنية على دفعات محدودة الذاكرة وتوثق طريقة حسابها؛ احتفظ بالفيديو المصدر خارجيًا لإعادة الاختبار.

## سياسة retries والتحقق

الانقطاع/مهلة/5xx: أعد نفس المعرفات بتراجع زمني وحفظ محلي. 401 أوقف الموصل وراجع انتهاء/إبطال المفتاح؛ 403 لا توسع صلاحياته تلقائيًا؛ 400/413 صلّح الحجم والمدخل، و409 راجع المراجعة أو قفل اليومية. افصل طابور البيانات عن حلقة تحليل الفيديو. النسخة الحالية حدود طابورها ١٠٠٠ سجل/٦٤MiB وتتوقف عند امتلائه، فلا تعتمد عليه لحفظ فيديو يوم كامل.

قبل الربط النهائي اختبر مطعمًا غير مسموح ومفتاحًا منتهيًا/ملغى ودور مهندس بلا POS، إعادة نفس الدفعة، تعارض revision، يومًا معتمدًا وحدود القاهرة، وانقطاعًا ثم تعافيًا. اختبارات الخادم الحالية تغطي هذه القيود الأساسية؛ الربط الفعلي بمورد الكاشير وNVR يحتاج بياناته واختبارًا مستقلًا.

## كتالوج موسع وحفظ الصور

`GET /api/recognition/classes` يعرض٨٠ اسمًا أصليًا بعناوين عربية. أنشئ/عدّل عنصرًا عبر `/api/dishes` و`/api/dishes/{id}` مع `kind` و`recognitionMode` و`detectorClasses`؛ احتفظ بـdishId في الربط حتى للأشياء العامة. الصور المرجعية تقبل `variantLabel` وتبقى جميع أشكال تقديم الصنف بنفس المعرف. التعيين المتعارض لفئة جاهزة لا يُحسم عشوائيًا.

الصور في مخزن filesystem خاص مستقل، والقاعدة تحمل `image_key,media_status`؛ استخدم `url/snapshot_url` المحميين لاستدعاء الصورة. إذا جاء `mediaPending>0`، حُفظت metadata بالفعل لكن الصورة تحتاج إعادة إرسال: احتفظ بالبايتات الأصلية وأعد نفس identity/payload، دون زيادة العدد المحلي ثانية. تعارض محتوى الصورة الأصلية409؛ غياب/تلف ملف يحتاج الأصل أو backup. لا تحوّل key إلى رابط bucket عام.

الأشخاص والأشياء العامة لا تدخل مدخلات POS الجديدة؛ هدف الكاشير مقارنة الأطباق والمشروبات. ملخص صورة ثابتة هو وجود عناصر فقط، وليس خروج طلبات. خطوات نسخة DB+media والتحقق والاستعادة موثقة في [التشغيل](OPERATIONS.md)، ومتطلبات السيرفر في [السحابة](CLOUD_REQUIREMENTS.md).
