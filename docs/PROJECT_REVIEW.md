# IEP — مراجعة المشروع بعد الإصلاحات

المشهد المستهدف: نقطة خروج أطباق واحدة بعرض لا يتجاوز مترًا، حتى أربعة عناصر في نفس الوقت، ونقطة مشروبات مشابهة. هذه مراجعة النسخة التجريبية بعد تنفيذ الإصلاحات وقياسات السعة وإضافة إدارة المخاطر والصلاحيات والربط. [المراجعة الأصلية](PROJECT_REVIEW_INITIAL.md) محفوظة كتاريخ للمشكلات؛ حالتها القديمة لا تصف النسخة الحالية.

## القرار الحالي

البرنامج مناسب لتجارب فيديو قصيرة ومقسمة، وتعريف أصناف المطعم، ومراجعة نتائج منفصلة عن الإنتاج ومقارنتها يدويًا مع الكاشير. **لم يثبت جاهزًا للتشغيل الآلي النهائي**: دقة الأطباق الحقيقية غير مقاسة، ومسار المتصفح الحالي بطيء على بيئة الاختبار، وخدمة edge وربط Hikvision/NVR وتشغيل ٢٤ ساعة متواصلة لم تنفذ.

## تنفيذ أخطاء المراجعة السابقة

| المعرف | ما نُفّذ | دليل التحقق |
|---|---|---|
| R1 — انتقال POS بين الأيام | تصفير كل سياق يوم/مطعم، تعطيل الحفظ أثناء التحميل، تجاهل ردود سياق قديم | اختبارات متصفح انتقال يوم وتأخر استجابة |
| R2 — ضياع تاريخ الصنف | أرشفة بدل حذف؛ المعرف محفوظ؛ أسماء POS وتوقعاته التاريخية ظاهرة | اختبار خادم للأرشفة وتاريخ POS وعدم إعادة استخدام المعرف |
| R3 — الشبكة توقف التحليل | إرسال مستقل عن التحليل، انتظار حفظ محلي فقط، مهلة وإعادة محاولة وحدود طابور | اختبار إرسال معلق، outbox بعد reload، وعدم مضاعفة الإرسال |
| R4 — اختلاف إطار الكشف والتصنيف | canvas واحد محدود الحجم للكشف والقص والاستقرار واللقطة، وحفظ لقطة العبور الأصلي حتى تأكيده | اختبارات pipeline؛ دقة المطعم تحتاج فيديو حقيقي |
| R5 — فيديو متجمد يبدو سليمًا | متابعة frame callback/عداد الإطارات وزمن وصول جديد؛ حالة stalled وفجوات محفوظة | اختبار بث بإطار واحد ثم توقفه |
| R6 — فجوة جلسة قديمة ممتدة | sourceId ثابت مستقل عن session، تحديد نهاية جلسة وفجوة المصدر عند التعافي | اختبار إعادة جلسة لنفس المصدر وعدم إغلاق مصدر آخر |
| R7 — فقد العبور المبكر | حفظ مرشح عبور إلى استقرار التصنيف بزمنه الأصلي؛ غير المؤكد مسجل للمراجعة عند اكتشافه | اختبارات تتبع عبور مبكر وتبديل اسم وانعكاس وانتهاء مرشح |
| R8 — حدود القاهرة الصيفية | حساب مركزي لفترة اليوم بنطاق نصف مفتوح | اختبار يوم ٢٣/٢٥ ساعة وحدود التقرير والمطابقة |
| R9 — قراءة التاريخ كاملًا | SQL بفهرس ونطاق يوم وتجميع؛ pagination زوج الوقت/ID للتاريخ | قياس مليون سجل metadata؛ اختبار صفحات وتعادل أوقات وأحداث متأخرة |
| R10 — تشغيل غير قابل للتكرار | README عام، Playwright مثبت، ملف MP4 تجريبي مولد، فحص SHA256 واستدلال نماذج حقيقي محفوظ | npm test وtest:browser وtest:models |

أثناء المراجعة الأمنية الأخيرة أُصلح أيضًا تجاوز محتمل لنطاق المطعم باستخدام restaurantId مزيف مع رابط صورة/حدث: التحقق الآن يتبع المطعم الحقيقي للمورد في الرابط أولًا. اختبار staff ومفتاح ربط يقيدان القراءة والحذف ضمن نطاقهما.

«أُصلح» هنا يخص العيب البرمجي الموثق، وليس ضمان عدم فقد أي طبق في الواقع. شروط الاختبار والقياس موضحة في الملفات أدناه.

## القدرات الجديدة

- شاشة مخاطر لكل مطعم: تقييم وإجراء ومسؤول وملاحظات، وقبول/إغلاق بمدير ودليل مكتوب.
- خمسة أدوار داخل حساب العميل، نطاق مطاعم لكل موظف، شاشة إنشاء/تعديل/تعطيل، وجلسات ومفاتيح تُبطل عند تعديل الحساب.
- مراجعة يومية مرتبطة بمراجعة POS، قفل تعديل يوم معتمد وإعادة فتحه، وعودة «تحتاج مراجعة» بعد أحداث حية متأخرة أو مجهولة أو تصحيحات.
- عبورات غير مؤكدة محفوظة للمراجعة، تأكيد/استبعاد دون مضاعفة، وتصحيحات عد تحفظ الأصل وتنعكس في التقرير والمطابقة. أحداث التجارب تظل منفصلة.
- شاشة API، OpenAPI قابل للتنزيل، مفاتيح محدودة ومنتهية قابلة للإبطال، ومرجع ربط الكاشير ومصدر المعالجة.
- تجربة فيديو على أجزاء، بصمة ملف محدودة الذاكرة، بصمات النماذج والمراجع والإعدادات، وشاشة تقدير السعة والمساحة وطابور الإرسال.

## نتائج السعة وما تعنيه

كاميرتان بمعدل ٢Mbps تعملان ٢٤ ساعة تحتاجان **٤٣٫٢GB فيديو/يوم، نحو ١٫٣TB/٣٠ يومًا** قبل هامش القرص والنسخ الاحتياطي. ٥٠٠٠ لقطة يومية ×٨٠KB تضيف نحو ٤٠٠MB/يوم. التطبيق الحالي لا يخزن الفيديو الكامل؛ هذه ميزانية NVR/التسجيل الخارجي المقترح.

الكشف الحقيقي وتصنيف أربع قصاصات على ٦٤٠×٣٦٠ استغرق في القياس نحو **٤٫٦٤ ثانية/إطار CPU** أو **١٫٥٣ ثانية WebGL برمجي SwiftShader**. هذه ليست GPU ولا دقة فعلية. استقراء فيديو يوم كامل بعينة ٥fps هو نحو ٥٥٧ ساعة أو ١٨٤ ساعة معالجة لكل كاميرا، قبل فك الفيديو وبقية العمل؛ **ليس قياسًا لتشغيل يوم كامل**. لهذا يجب تحسين مسار المعالجة واختبار edge على العتاد المستهدف قبل اختياره.

مليون حدث metadata دون صور شغل نحو ١٦٠٫٦MB SQLite؛ API يوم فيه ٥٠٠٠ حدث استغرق متوسطًا نحو ٤–٧ms في اختبار محلي محدود. هذا يثبت تحسين القراءة، ولا يثبت أداء مليون صورة أو ضغط عدة عملاء أو سلامة backup. [القياسات والمعادلات ومتطلبات الخادم والتشغيل](CAPACITY_AND_OPERATIONS.md).

## التحقق وحدوده

`npm test`: نجح **٢١ اختبارًا، صفر فشل وصفر تخطي**. يغطي الخادم والصلاحيات والعزل والتوقيت والتتبع والتصحيحات والتعافي والصفحات. `npm run test:browser` نجح في جميع سكربتاته الأربعة، ويغطي outbox/CSV/الفيديو الاصطناعي والأخطاء السابقة والشاشات الجديدة والصلاحيات في المتصفح. `npm run test:models` نجح؛ يتحقق من بصمات الملفات ويشغل النماذج الحقيقية على ثلاثة إطارات اصطناعية. نجاح الكشف الاصطناعي لا يقيس صحة المطعم؛ تقرير التنفيذ النهائي يذكر نتائج التشغيل الفعلية.

لم تُختبر كاميرا Android فعلية أو Hikvision أو انقطاع كهرباء حقيقي أو استرجاع NVR أو GPU أو تشغيل متواصل ٢٤ ساعة أو استعادة backup. لا يوجد رابط HTTPS عام متاح من هذه البيئة. بناء Docker لا يُعتبر مجربًا لمجرد وجود Dockerfile.

## قيود باقية وخطة قبول

1. صور المرجع لا تدرب detector خاصًا؛ الكاشف العام قد يفوّت طبقًا مسطحًا أو كوبًا محجوبًا، والأكواب المتطابقة لا تكشف محتواها بالضرورة. التشابه ليس نسبة دقة.
2. المجهول محفوظ عندما يُكتشف عبوره؛ غياب الكشف أصلًا لا يضمن سجل استثناء. استمرار/إعادة هوية جسم مادي بعد اختفاء طويل وإعادة تشغيل ليست ضمانًا قائمًا.
3. POS يومي مجمع، لا يربط كل طبق بطلب محدد. راجع الكومبو والوحدة والإلغاء قبل/بعد الخروج والمرتجعات والمجاني والهالك. اليوم التقويمي في القاهرة؛ تغيير بداية الوردية يحتاج تنفيذًا.
4. تصحيح السجل وحفظ الأصل موجودان، لكن مسؤول نظام التشغيل يستطيع تغيير SQLite. MFA، تنبيهات خارجية، سجل غير قابل للتعديل، retention وخدمة edge وbackup مجرب تحتاج تجهيز الإنتاج.
5. الفروق حالات مراجعة؛ لا تثبت سرقة أو تحدد شخصًا. اعتماد اليوم مراجعة مدير مع إقرار القيود، ويمكن للمدير إدخال الكاشير واعتماده؛ الفصل الصارم بين شخصين غير مفروض.
6. قبل شراء الأجهزة: فيديو مستقل معلّم بشريًا لكل نقطة، اختبار ١/٢/٤ عناصر والأيدي والصواني والعودة والإضاءة، حدود قبول للفائت والمكرر والخطأ والمجهول؛ بعدها وردية كاملة وكهرباء وشبكة ونسخ احتياطي على العتاد المختار.
