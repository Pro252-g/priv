# IEP — النماذج والبيانات وتحسين التعرف

## الكشف والتعرف عمليتان

الكاشف يجد موضع العنصر، ثم مقارنة مرجعية تقترح صنف المطعم داخل الموضع. صور بيتزا متعددة تحسن المقارنة بعد العثور عليها، ولا تدرب الكاشف على اكتشاف طبق لم يجده. COCO80 يشمل bowl/cup/pizza وأشياء كثيرة، **ولا يشمل plate**. أكواب مغلقة متطابقة لا تكشف المشروب داخلها بالصورة وحدها؛ عدها كأكواب أو أضف قرينة POS/موقع التحضير.

المتصفح يستعمل COCO SSD وMobileNet؛ العامل يستعمل YOLOXtiny وMobileNetV2 features1280 على CPU. cosine similarity ليست احتمال صحة معايرًا؛ threshold وmargin يضبطان على اختبار مستقل. النماذج ليست تعرفًا غير محدود، ولا تثبت هوية فيزيائية بعد حجب طويل أو بين الكاميرات.

## تجهيز ملفات متحققة

Ubuntu/Python3.12 x86_64 هو مسار البناء المختبر. Torch أدوات بناء فقط؛ تشغيل العامل لا يستوردها:

```sh
python3 -m venv .local/edge-venv
.local/edge-venv/bin/pip install -r edge/requirements.txt
.local/edge-venv/bin/pip install --index-url https://download.pytorch.org/whl/cpu torch==2.5.1 torchvision==0.20.1
.local/edge-venv/bin/pip install onnx==1.17.0
.local/edge-venv/bin/python scripts/setup-edge-models.py --output .local/edge-models
```

السكريبت ينزل عبر TLS ويتحقق من SHA256 ويصدر features1280 بـopset13. ملف مختلف البصمة يُرفض؛ لا تغير البصمة لقبوله. manifest.json يسجل المصدر والحجم والترخيص والإصدارات وطبيعة البصمة. تصديران على البيئة الحالية أعطيا ملفًا مطابقًا byte-for-byte؛ تحقق على منصة البناء المستهدفة قبل توزيع حزمة offline.

| الملف | SHA256 | المصدر |
|---|---|---|
|yolox_tiny.onnx|`427cc366d34e27ff7a03e2899b5e3671425c262ea2291f88bb942bc1cc70b0f7`|[YOLOX0.1.1rc0](https://github.com/Megvii-BaseDetection/YOLOX/releases/tag/0.1.1rc0)، Apache2؛ hash مثبت من HTTPS وليس توقيع ناشر |
|mobilenet_v2-b0353104.pth|`b03531047ffacf1e2488318dcd2aba1126cde36e3bfe1aa5cb07700aeeee9889`|[Torchvision weights](https://download.pytorch.org/models/mobilenet_v2-b0353104.pth)، [BSD3](https://github.com/pytorch/vision/blob/v0.20.1/LICENSE)؛ بادئة hash منشورة في الاسم |
|mobilenet-v2-features.onnx|`e58c623b9269fd171e6cc35ec401e0a72c69b1baad2e2e21c06b444c902fd5a9`|تصدير IEP من الأوزان السابقة؛ features `[1,1280]` وليس logits |

YOLOX input float32 `[1,3,416,416]` BGR0..255 مع top-left letterbox114، output `[1,3549,85]` غير decoded وstrides8/16/32. MobileNet input `[1,3,224,224]` RGB/255، mean `[.485,.456,.406]` وstd `[.229,.224,.225]`. تغيير preprocessing يغير النتائج.

يمكن تشغيل العامل في venv runtime فقط مع نسخ ONNX وmanifest من بيئة البناء. لا ترفع بيانات العملاء أو الأوزان إلى Git. راجع تراخيص الكود والأوزان والبيانات الخاصة بالتدريب قبل التوزيع التجاري؛ ترخيص framework لا يحسم حقوق كل dataset.

## نموذج المطعم المخصص

لا توجد بيانات مطعم مقدمة ولم ندرب نموذج مطعم. اعتماد الأطباق يحتاج كاشف plate/drink_container أو كاشف أصناف مباشر يناسب زاوية الشباك. العامل يدعم عقدين محددين:

- `format:yolox`: ترتيب الفئات ومخرجات YOLOX raw/decoded مطابقان للإعداد.
- `format:xyxy`: صفوف float32 `[x1,y1,x2,y2,score,classIndex]`، classIndex صفر أساس، top-left letterbox، وإحداثيات pixels افتراضيًا أو normalized مع `boxSpace:normalized`. input preprocessing معلن وlabels بالترتيب نفسه.

**تصدير YOLOv8/YOLO11 إلى ONNX لا يجعله متوافقًا تلقائيًا.** مخرجاته المعتادة مختلفة؛ يلزم wrapper إلى العقد أو adapter جديد مختبر. النسخة لا تقدم مدربًا آليًا أو تنزيلًا تلقائيًا للنماذج المخصصة.

سجل model profile بالنسخة وSHA والفئات في API/الواجهة، واربط المصدر به، ثم ضع الملف وlabels والبصمة في JSON الخاص بالجهاز. العامل يرفض اختلاف النموذج أو الفئات أو المعايرة. تسجيل metadata لا يدرب أو يثبت الدقة، ولا يغير كاشف المتصفح.

## خطة البيانات والتحسين والقبول

1. اجمع فيديو من الزاوية الثابتة لكل شباك: أوقات الوردية والإضاءة والبخار والأيدي والصواني و1–4 عناصر واختلاف الأواني والحصص، مع إطارات فارغة وعناصر غير مطلوبة.
2. ضع صناديق لوحدة الخروج المتفق عليها؛ لا صندوقين للطعام والحاوية لنفس الوحدة. سجل الصنف وشكل التقديم والوقت والنقطة. للمشروب المخفي اختر تعريفًا بصريًا ممكنًا بدل اسم غير قابل للرؤية.
3. افصل train/validation/test حسب يوم أو مقطع كامل؛ لا توزع إطارات متجاورة عشوائيًا بين المجموعات. احتفظ باختبار لم يدخل المراجع أو ضبط threshold. عدد صور ثابت لا يضمن الدقة؛ يحدد من منحنى الأخطاء والفئات الصعبة.
4. درب الكاشف وصدر العقد الصحيح، وسجل dataset/model version وSHA والأداء لكل فئة والعتاد والترخيص. للمقارنة المرجعية أضف صورًا مقصوصة واضحة لكل تقديم تحت نفسdishId؛ الخلفية قد تسبب تطابقًا خاطئًا.
5. قارن كل خروج بعد بشري موثق: missed/duplicates/wrong-class/unknown والفجوات. دقة صناديق الكشف تختلف عن دقة العد. افصل النتائج حسب الصنف والنقطة والإضاءة، ولا تخف الأخطاء النادرة خلف المتوسط.
6. اتفق مع العميل على أهداف قبول وعينة وثقة إحصائية. مثال تفاوضي **غير محقق حاليًا**: ≥99% صحة عبور و≥98% تعريف للفئات الممكنة بصريًا، مع مراجعة المجهول ورفض اعتماد تغطية ناقصة.
7. شغّل shadow mode ثم وردية و24h تتضمن انقطاعًا وعودة وحرارة. أعد الاختبار بعد تغيير الزاوية/الإضاءة/الأواني/الوصفة/النموذج، مع نسخة سابقة وrollback.

## عدم التعرف وحدود الاختبارات

صندوق يعبر مع تشابه ضعيف/تعارض/تغير اسم ينتج مجهولًا ولا يزيد صنفًا مؤكدًا حتى مراجعة المدير. عنصر بلا صندوق قد يفوت النظام ولا ينتج مجهولًا؛ يكتشف ذلك بعد بشري وفيديو تحقق. تعطل المصدر أو النموذج أو cadence ينتج فجوة ويتوقف العد الآمن. health يثبت توفر المعالجة لا صحة كل عدد.

اختبار الربط الحقيقي استخدم [YOLOX dog.jpg العامة](https://raw.githubusercontent.com/Megvii-BaseDetection/YOLOX/main/assets/dog.jpg) في فيديو متحرك، وتحقق من عبور واحد ولقطة خاصة وإعادة آمنة. ليس قياس أطباق مطعم أو NVR فعلي. أمره `node scripts/edge-integration-check.mjs PATH_TO_DOG_IMAGE` بعد تجهيز النماذج. [قياسات السعة](CAPACITY_AND_OPERATIONS.md) تفصل الاستقراء عن التجربة.
