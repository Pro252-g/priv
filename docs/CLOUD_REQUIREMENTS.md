# IEP v0.4 — متطلبات الكلود والتخزين والتكلفة

تحديث 2026-10-09. خريطة التركيب والأوامر في [دليل التنفيذ](EXECUTION_GUIDE.md)، وحالة الاختبارات وحدود القبول في [مراجعة المشروع](PROJECT_REVIEW.md). ملفات النشر جاهزة للمراجعة والتجربة؛ لم يُحجز خادم أو نطاق أو يُنشر رابط HTTPS عام خلال هذا العمل.

## الاختيار المقترح

**NVR للفيديو الأصلي، جهاز داخل المطعم للتحليل، وكلود للنتائج واللقطات والتقارير.** هذا هو مسار البداية: Ubuntu 24.04 على جهاز edge وعلى VPS، خدمة systemd للمصدر، و Docker Compose مع Caddy HTTPS للموقع. لا نحتاج GPU في خادم الموقع، ولا نسخة كاملة ثانية من تسجيل NVR.

العامل الأصلي Python/OpenCV/ONNX CPU موجود الآن لمصدر RTSP أو USB أو ملف تجربة، مع طابور محلي وإعادة اتصال وتشخيص ومزامنة. يستخدم كاشفًا عامًا ومراجع، وليس نموذج مطعم معتمدًا. لا توجد خدمة ONVIF discovery أو تنزيل أرشيف Hikvision أو backfill تلقائي للتشغيل. النماذج والزاوية والعتبات تحتاج معايرة واختبارًا مستقلًا لكل عميل.

| المكان | ما يُحفظ | الغرض |
|---|---|---|
| NVR | الفيديو الأصلي حسب ساعات ومدة احتفاظ الجهاز | المراجعة والأدلة خلال فترات التصوير |
| جهاز edge | طابور SQLite، cache المراجع وملف health والإعدادات الخاصة | تحليل ومزامنة بعد انقطاع الإنترنت؛ لا تكرار تسجيل الفيديو |
| volume قاعدة الكلود، `/data` | SQLite و WAL/SHM و metadata والتدقيق والمراجعات ومفاتيح الصور | المستخدمون والأصناف والأحداث والكاشير |
| volume الصور، `/media` | المراجع وقصاصات known/unknown | صورة تُستدعى عند طلب مخول |
| وجهة نسخ خارج الخادم | DB+media متحققان ومشفران بسياسة المشغل | الاستعادة من عطل الخادم أو فقد الأقراص |

## السيرفر المبدئي

| النطاق | مواصفات مبدئية | ما يُقاس قبل التوسع |
|---|---|---|
| مطعم واحد أو تجربة أولى | 2 vCPU، RAM 4 GB، SSD دائم 80 GB، شبكة HTTPS، نسخة خارج الخادم | حمل API، رفع الصور، المستخدمون المتزامنون، مساحة DB/media والنسخ |
| عدة مطاعم في بداية التجربة | 4 vCPU و 8 GB، SSD أكبر وفق مجموع الصور والاحتفاظ | اختبار حمل وتزامن الرفع وحدود العملاء؛ لا وعد بعدد مطاعم |
| انتشار أكبر | خطة DB وخزن صور ومهام قابلة للتوسع حسب القياس | PostgreSQL و S3 ليسا adapters مفعلة في الإصدار الحالي |

المقترح 80 GB **إجمالي بداية** يشمل نظام التشغيل والحاويات والبيانات والصور وسجلاتها؛ تقسيمه إلى volumes لا يضاعف القرص. لا تختَر قرصًا قريبًا من الامتلاء، ولا تحجزه دون حساب مدة الاحتفاظ. خادم 2 vCPU/4 GB لا يُكلف بتحليل بث الكاميرات في هذه البنية.

SQLite الحالية خدمة واحدة على قرص محلي. لا تشغّل عدة replicas تكتب نفس الملف عبر NFS؛ زيادة instances ليست خطة توسع لهذه القاعدة. القياس السابق لمليون حدث بلا صور ≈160.6 MB، وتقارير اليوم ≈6.73 ms عبر localhost، قبل أعمدة الإصدار الحالي. ليس ذلك اختبار حمل للنشر أو مليون صورة؛ [تقرير السعة](CAPACITY_AND_OPERATIONS.md) يفصل الأدلة.

## النشر المنفذ في المستودع

`deploy/compose.yml` يعرّف API و proxy Caddy ومهمة backup ضمن profile `maintenance`. Node لا يُنشر مباشرة للإنترنت؛ 80/443 عند proxy، و API على شبكة backend داخلية. هوية proxy معروفة ويُحدد `IEP_TRUSTED_PROXY_IPS` لها فقط؛ تغيير subnet أو IP يتطلب تحديث الإعدادات معًا، ولا تُوثق أي X-Forwarded-For عشوائية.

الحاويات بمستخدم 1000:1000، نظام ملفات أساسي للقراءة فقط، إسقاط capabilities وسياسة restart، مع volumes دائمة. الصيغة الفعلية وتهيئة ملكية volumes وشهادات DNS/HTTPS وبناء الصور والخطوات الأولى في [دليل التنفيذ](EXECUTION_GUIDE.md). لا تعد نجاح API health إثباتًا لعمل كاميرا المطعم؛ health المصدر والموديل والطابور منفصل.

| المتغير أو المجلد | المعنى |
|---|---|
| `IEP_DATA_DIR=/data` | قاعدة بيانات خاصة، WAL/SHM و snapshot الترحيل |
| `IEP_MEDIA_DIR=/media` | مخزن الصور الخاص؛ filesystem محلي وليس bucket عامًا |
| `IEP_MODELS_DIR` | نماذج المتصفح المحلية؛ منفصلة عن ONNX الخاص بجهاز edge |
| `IEP_SECURE_COOKIE=true` | كوكي الدخول عبر HTTPS |
| `IEP_TRUSTED_PROXY_IPS` | عنوان proxy الموثوق فعليًا |
| `IEP_ADMIN_PASSWORD` | سر إعداد المدير؛ يوضع محليًا في ملف env محمي، لا في Git أو الدليل |

المجلدات الخاصة 700 والملفات 600. المسارات تُفحص عبر realpath وأقرب parent موجود؛ data/media داخل public أو symlink إليه مرفوضان، وخدمة static ترفض رابطًا إلى الملف الخاص. GET الصورة يتحقق من الصلاحية والعميل والمطعم؛ معرف صورة أو URL وحده لا يمنح القراءة.

## حساب مساحة الصور والاتصال

5000 حدث/يوم ×80 KB لقطة =400 MB/يوم أو **12 GB/30 يومًا** قبل DB والصور المرجعية والنسخ. حجم 80 KB افتراض تصميم يحتاج قياسًا من قصاصات المطعم، ورفع JSON/base64 يزيد traffic نحو ثلث حجم الصورة مع overhead. لا يساوي 12 GB حجم طابور edge أو نسخ 30 يومًا كاملة.

| مدة حفظ الصور عند نفس الافتراض | مساحة الصور وحدها |
|---|---:|
| 30 يومًا | 12 GB |
| 90 يومًا | 36 GB |
| 365 يومًا | 146 GB |

لا توجد سياسة حذف آلي حسب المدة لكل عميل منفذة. 80 GB لن يسع سنة من هذا الحمل مع الإضافات. حدّد مدة الصور بحسب حاجة المراجعة وسياسة العميل، ثم راقب الحجم وأضف التخزين قبل الامتلاء. لا تحذف ملفات media يدويًا لإفراغ قرص؛ ذلك يترك مرجعًا مفقودًا ويضعف الدليل. النسخ الكاملة الإضافية تحتاج تقريبًا نفس حجم DB+media؛ نسخة كل يوم لمدة 30 يومًا قد تستهلك أضعافًا كبيرة.

داخل LAN، كاميرتان ×2 Mbps ≈4 Mbps بث قبل الهامش؛ Ethernet مفضل بين NVR والجهاز. لا تنقل هذه البنية الفيديو إلى الكلود، بل النتائج والقصاصات عبر HTTPS outbound. انقطاع الإنترنت يراكم outbox ضمن حدوده؛ فقرة الفشل في [التشغيل](OPERATIONS.md) تحدد الإجراء عند auth أو storage أو queue blocked.

## إذا تقرر تحليل الفيديو داخل الكلود

العامل CPU الأصلي يمكنه العمل على جهاز يرى RTSP عبر شبكة خاصة؛ نشره قرب API لا يعطيه وصولًا تلقائيًا إلى LAN المطعم. يلزم VPN أو بوابة داخلية تضبطها الجهة المشغلة؛ لا تفتح NVR/RTSP أو تضع أسراره في واجهة المستخدم. إضافة GPU إلى خادم Node لا تسرع متصفح الهاتف أو عامل CPU الحالي؛ runtime GPU/CUDA يتطلب تنفيذًا وقياسًا مستقلًا.

كاميرتان عند 2 Mbps طوال 24 ساعة ≈43.2 GB/يوم أو 1.296 TB/30 يومًا من نقل الفيديو، دون overhead. تحتاج سرعة رفع مستقرة أعلى من 4 Mbps مع هامش؛ سرعة اشتراك الإنترنت لا تثبت سرعة الرفع المستمر. حفظ الفيديو يبقى على NVR حتى لو استقبل عامل cloud البث، إلا إذا اختار العميل تسجيلًا آخر صراحة.

| خيار قيد التقييم | مواصفات مرشحة | الحد المعروف |
|---|---|---|
| CPU cloud inference مستقل | 4–8 vCPU و RAM 16 GB مبدئيًا | قياس عاملين مع فك البث والنقل مطلوب؛ ليس قياس VPS فعليًا |
| GPU worker مستقبلًا | 4–8 vCPU، RAM 16–32 GB و GPU 16 GB مثل T4 مرشح | لم يُنفذ runtime GPU ولم يُقس هذا الجهاز؛ لا حجز طويل قبل الاختبار |
| ويب/API | يبقى على حصة مستقلة | حتى لا تؤخر معالجة الفيديو الدخول والتقارير |

القياس الأصلي المحدود: عامل واحد ≈114.56 ms، وعاملان ≈147.27/163.41 ms لمركب كشف وأربع قصاصات و 60 vector وتتبع و 4 JPEG. لا يشمل decode/RTSP/قرص/HTTPS. البيئة أربعة CPU في cgroup مشتركة؛ p95 للعامل الثاني 228.12 ms يتجاوز فترة 200 ms لهدف 5 fps. ليس ضمانًا لكاميرتين فعليتين أو CPU المطعم؛ انظر [الدليل المحفوظ](review-evidence/edge-capacity-2026-10-09.json).

## النسخ والتشفير وفقد الصور

أداة `npm run backup` المنفذة تنشئ snapshot SQLite متسقًا، وتنسخ الصور المرتبطة، وتتحقق من SHA والحجم، وتستعيد إلى مسارات جديدة فقط. hashing يقرأ على دفعات 1 MiB، والتحقق من المراجع خطي؛ manifest و Map ينموان مع عدد الصور. الصور المستعادة السليمة تُصحح حالتها إلى ready حتى إذا كان snapshot pending، فلا يحتاج المشغل GET يدويًا لإصلاح المراجع.

مهمة Compose تحفظ نسخة على volume `api_backups` **على نفس الخادم**. لا توجد عملية نقل خارج الجهاز أو تشفير أو جدولة أو حذف نسخ تلقائي. عيّن جدولًا ومسؤولًا و RPO/RTO، وانقل النسخة المتحققة إلى وجهة خارجية مشفرة، ثم اختبر الاستعادة على أقراص النشر. التشفير at rest يتطلب أقراصًا ومفاتيح من المشغل؛ filesystem adapter لا يشفّر ملفاته تلقائيًا.

ملف missing/corrupt لا يُعتبر ready لمجرد وجود نفس الحجم؛ SHA صحيح شرط التعافي. نتيجة `mediaPending` تحتفظ بطلب الصورة في outbox لإعادة إرسالها دون مضاعفة العدد. استعادة DB+media ليست تبديلًا ذريًا بين قرصين: استعد إلى مسارين جديدين، أوقف التطبيق، بدّل إعدادات المسارين معًا، وتحقق قبل إعادة الفتح. [إجراءات النسخ والفشل](OPERATIONS.md) مرجع التشغيل.

## التكلفة والقرار النهائي

لم يُحدد مزود أو منطقة أو عرض سعر حي. الميزانية تجمع VPS والتخزين الدائم ونمو الصور والنسخ الخارجية و bandwidth/egress والنطاق وتشغيل وصيانة Ubuntu، والجهاز والكاميرات و UPS والتركيب. cloud GPU بند مختلف يتوقف على ساعات المعالجة؛ غير مطلوب لبداية edge+cloud.

قبل الشراء والاشتراك: حدد ساعات العمل والاحتفاظ والعميل الأول؛ اختبر i5-1235U/16 GB/512 GB مرشحًا مع كاميرتين فعليتين؛ راجع 24 ساعة ودقة مجموعة المطعم والانقطاع والاستعادة والصلاحيات. دليل التركيب قابل للتنفيذ، والقبول الميداني مازال شرطًا قبل وصف الخدمة بالجاهزة تجاريًا.
