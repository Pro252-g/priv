# IEP — متطلبات السيرفر والسحابة والتخزين

## التوصية العملية

لتركيب المطعم النهائي نرشح **NVR يحتفظ بالفيديو داخل المكان، ومعالجة محلية على جهاز edge، وسحابة تحفظ النتائج والصور المختارة وتعرض التقارير**. هذا يقلل نقل الفيديو ويتيح استمرار العد عند انقطاع الإنترنت. توجد الآن معالجة متصفح وواجهات وتخزين ومراجعة؛ موصل RTSP وخدمة edge المستقلة والنموذج المخصص لم تُعتمد بعد. يمكن اختبار الوظائف والدقة على مقاطع محلية قصيرة دون شراء GPU أو رفع فيديو يوم كامل للسحابة.

| أين توجد البيانات؟ | الاستخدام | هل يحفظ فيديو كاملًا؟ |
|---|---|---|
| NVR المطعم | التسجيل الأصلي ومراجعة فترة انقطاع المعالجة | نعم، حسب إعداداته وسعته، خارج التطبيق |
| ملف فيديو على جهاز التجربة | تحليل مقطع محلي وإعادة مراجعة الأصل | يبقى عند المستخدم؛ لا يرفعه التطبيق كاملًا |
| قاعدة البيانات `IEP_DATA_DIR` | الأصناف والعد والمراجعات والمبيعات والمخاطر والمستخدمون وبصمات الصور | لا |
| مخزن الصور الخاص `IEP_MEDIA_DIR` | صور مرجعية ولقطات أحداث معروفة ومجهولة | لا، صور فقط |

الفصل بين قاعدة البيانات والصور يقلل حجم SQLite ويسهل توسيع التخزين. المخزن المنفذ للصور **adapter قرص محلي خاص** خارج ملفات الموقع العامة؛ ليس تكامل S3 أو رفع فيديو إلى cloud object storage. عند اختيار S3/MinIO لاحقًا يلزم تنفيذ adapter وأذونات وسياسة احتفاظ واختبارات استعادة، لا يكفي وضع رابط bucket في متغير بيئة.

## خادم الويب وAPI فقط

التحليل الحالي يعمل في متصفح الهاتف أو الكمبيوتر، لا داخل عملية Node. إضافة GPU لسيرفر الموقع وحدها لا تسرع المتصفح. هذه المواصفات نقاط بدء لتجربة حمل حقيقي، وليست شهادة سعة أو ضمان عدد عملاء:

| النطاق | CPU وRAM مبدئيان | تخزين النظام والبيانات | ما يجب قياسه |
|---|---|---|---|
| مطعم واحد، تقارير وAPI | ٢vCPU /٤GB RAM | SSD دائم٤٠–٨٠GB، مع volume صور مستقل حسب الاحتفاظ | زمن API، تزامن المستخدمين، رفع الصور، الذاكرة ومساحة القرص والنسخ |
| عدة عملاء في بداية التجربة | ٤vCPU /٨GB RAM | SSD دائم مع تخزين صور منفصل وحصص لكل عميل | load test متعدد العملاء؛ لا تقسيم حجم مطعم واحد فقط |
| انتشار تجاري | PostgreSQL وخزن صور خاص وعمال مهام حسب الحمل | نسخ واحتفاظ وتوسع مستقل | صيانة وتشغيل وصلاحيات وقياس نمو وتزامن؛ التصميم لم يُنشر كاملًا |

SQLite الحالي قرص محلي وخدمة واحدة؛ لا تشغّل replicas تشارك ملف قاعدة واحدًا عبر شبكة. PostgreSQL ليس adapter مفعلًا الآن. قاعدة مليون حدث **بلا صور** كانت نحو١٦٠٫٦MB؛ مطابقة٥٠٠٠ حدث يوميًا≈٤٫٢١ms وتقارير اليوم≈٦٫٧٣ms عبر localhost. هذا baseline قبل أعمدة تخزين الصور الجديدة، بلا معاملات رفع صور أو ضغط مستخدمين متزامنين، فلا تعتبره نتيجة نشر جديد أو وعد استجابة لكل العملاء.

## إذا اخترنا تحليل الفيديو في السحابة

هذه بنية مختلفة تحتاج عامل inference مستقلًا، لا مجرد خادم ويب أكبر. المطلوب:

1. بوابة داخل LAN المطعم تتصل بـNVR/RTSP وتفتح اتصالًا outbound آمنًا للسحابة، أو VPN خاص. لا تنشر منافذ NVR/RTSP أو أسماء الدخول للإنترنت، ولا تضعها في JavaScript المستخدم.
2. عامل GPU/CPU يتولى فك البث والكشف وتصنيف الأصناف والتتبع والتسجيل، مع queue محلي/سحابي وتوقيت مصدر وreconnect. يجب أن يُنتج الأحداث مرة واحدة بعد التعافي.
3. runtime محسّن ونموذج مناسب؛ CUDA/GPU workers وRTSP وbackfill ليست وظائف موجودة بمجرد توفير السيرفر. تطبيق TensorFlow.js المتصفحي لا يصبح خدمة CUDA تلقائيًا.
4. اختبار كاميرتين معًا، target أولي٥fps لكل كاميرا =١٠ إطارات تحليل/ثانية، مع أربع قصاصات محتملة لكل إطار وهامش للذروة. إذا كان عاملًا تسلسليًا واحدًا فهذا يحتاج متوسطًا أقل من١٠٠ms للإطار المركب قبل باقي المصروف؛ نختبر الدقة عند هذا المعدل بدل تحويل الهدف إلى ضمان.

| خيار تجربة cloud inference | المتطلبات المرشحة | حدود التوصية |
|---|---|---|
| GPU worker منفصل | CPU٤–٨vCPU، RAM١٦–٣٢GB، GPU بذاكرة١٦GB مثل NVIDIA T4 كمرشح، SSD للـqueue/cache | لا يوجد benchmark لهذا GPU أو runtime في المشروع؛ لا شراء أو حجز طويل قبل تجربة النموذج الحقيقي |
| CPU worker محسّن | CPU حديث وRAM كافية حسب قياس النموذج | المسار CPU الحالي بطيء جدًا؛ زيادة RAM لا تحل throughput، وقد يتطلب نموذجًا أصغر أو GPU |
| خادم ويب وتقارير | يظل منفصلًا أو محدود الحصة عن عامل inference | حتى لا تؤخر معالجة الفيديو عمليات الدخول والكاشير والمراجعة |

القياس الحالي الحقيقي على إطار٦٤٠×٣٦٠: كشف+أربع MobileNet قصاصات≈٤٫٦٤٣s CPU، أو١٫٥٣١s WebGL عبر **SwiftShader برمجي بلا GPU فعلي**. كلاهما غير مناسب لهدف١٠fps. يوجد اختبار وظائف ونماذج قصيرة، ولا يوجد اختبار دقة مطعم أو يوم كامل. يتطلب التشغيل النهائي runtime محسنًا ونموذجًا مخصصًا أو تقييم نموذج أسرع على جهاز العميل. [تقرير السعة](CAPACITY_AND_OPERATIONS.md) يشرح القياس واستقراء زمن يوم كامل.

## الإنترنت والتكلفة

بث كاميرتين عند٢Mbps لكل واحدة≈٤Mbps uplink مستمر قبل overhead، ويولد نحو٤٣٫٢GB/يوم أو **١٫٢٩٦TB خلال٣٠ يومًا** عند التشغيل٢٤ساعة. احتفظ بهامش فوق٤Mbps وقِس تذبذب السرعة والرفع وقت الذروة. لا نفترض أن خط الإنترنت المعلن٢٠Mbps يعطي uplink مستمرًا بهذه السرعة. الانقطاع يعني backlog إن أمكن تخزين البث محليًا؛ نقل بلا recording محلي قد يفقد الفيديو.

رفع النتائج والصور فقط أقل كثيرًا:٥٠٠٠ حدث يوميًا ×متوسط لقطة٨٠KB≈٤٠٠MB/يوم أو١٢GB/٣٠يوم، إضافة إلى metadata وصور المراجع ومراجعات المجهول. هذه افتراضات تصميم للقططات وليست أحجامًا مقاسة من مطعم. الـNVR يتحمل تسجيل الفيديو، ولا نكرر نسخه بالكامل إلى السيرفر افتراضيًا.

التكلفة تجمع اشتراك CPU/RAM أو GPU، ساعات تشغيل العامل، التخزين الدائم والنسخ، bandwidth/egress، HTTPS/النطاق، VPN وإدارة التشغيل. لا توجد عروض أسعار حية موثقة أو مزود معتمد؛ نطلب quote بحسب البلد والاحتفاظ وساعات التشغيل قبل أي اشتراك. توفير مبلغ GPU وهمي أو سعر ثابت دون هذه المتغيرات لن يثبت ميزانية المشروع.

## إعدادات التخزين وDocker

استخدم volume مستقلًا لقاعدة SQLite وvolume مستقلًا للصور. في Docker:

| المتغير | مسار الحاوية | ما يجب حفظه |
|---|---|---|
| `IEP_DATA_DIR` | `/data` | قاعدة البيانات وWAL/SHM عند نشاطها |
| `IEP_MEDIA_DIR` | `/media` | صور المرجع والأحداث ومفاتيحها وبصماتها |
| `IEP_SECURE_COOKIE` | `true` عند HTTPS | ليس ملف بيانات |
| `HOST` | `0.0.0.0` داخل الحاوية | يبقى port Node خاصًا خلف proxy |

اربط named volumes أو أقراص دائمة محددة بالمسارين؛ لا تعتمد على طبقة كتابة الحاوية أو anonymous volume لا تديره. صورة Docker تستبعد devDependencies وPlaywright. إن كان التخزينان على نفس القرص، الفصل تنظيمي لا يحميهما من فشل القرص؛ backup خارج الجهاز مطلوب. حذف volume الصور أو تعديل المسار بلا نقل آمن يترك سجلات تشير إلى صور مفقودة.

عند ترحيل نسخة قديمة تحتوي صور BLOB، يلزم الاحتفاظ بنسخة متسقة قبل التحويل، ثم كتابة الصورة خارج القاعدة والتحقق من البايتات والبصمة قبل إزالة BLOB. إعادة التشغيل ينبغي أن تتحمل التكرار بأمان؛ فصل الصورة لا يعني أن ملف SQLite سينكمش فورًا. تبقى الصفحات القديمة قابلة لإعادة الاستخدام؛ لتقليل الحجم الفيزيائي استخدم offline VACUUM بعد إيقاف الخدمة ونسخة مجرَّبة ومساحة إضافية كافية، لا VACUUM أثناء تشغيل إنتاج دون تخطيط.

## النسخ والخصوصية والتشغيل

الصور لا تُقدم من `/public`؛ طلبات GET تمر بتسجيل دخول أو مفتاح مسموح، والتحقق من العميل والمطعم وصلاحية القراءة. URL خاص لا يُستبدل بحماية bucket عامة. المفاتيح مؤقتة ومحدودة؛ لا تنسخ الأسرار إلى payload أو logs. التشفير at rest يتطلب أقراص/نسخ مشفرة وإدارة مفاتيح لدى الاستضافة؛ حفظ ملف محلي لا يثبت أنه مشفر تلقائيًا.

صورة وقاعدة متسقتان شرط استعادة: أوقف استقبال الكتابة في نافذة صيانة ثم انسخ DB مع الصور، أو استخدم آلية snapshot متناسقة مثبتة تحافظ على علاقة مفاتيح الصور بالقاعدة. نسخة SQLite online وحدها لا تنسخ volume الصور. أداة `npm run backup` المنفذة تنشئ online snapshot وmanifest بصمات DB والصور المرتبطة، وتتحقق وتستعيد إلى مسارات جديدة؛ اختُبرت على بيانات مؤقتة، وتكشف النسخة غير المكتملة. اتبع [الأوامر وإجراءات الاستعادة](OPERATIONS.md#أوامر-النسخ-والتحقق-والاستعادة-المنفذة)، ثم جرّبها على volumes الإنتاج وقراءة صور معلومة وأحداثها بحساب مخول. ضع سياسة RPO/RTO واحتفاظ وحذف حسب العميل؛ لا تدع حذف صورة خارج السياسة يزيل دليل مراجعة يوم مفتوح.

فعّل مساحة حرة وتنبيه فشل كتابة أو قراءة صورة، وحصص عميل، restart policy للخادم، ومراقبة queue وغياب إطارات ومصدر NVR. طابور المتصفح يكتب قبل إرسال الحدث ويعيد المحاولة عند فشل الشبكة/الحفظ؛ يحفظ الصور المعلّقة ضمن payload. التخزين المحلي قد يُمحى أو يمتلئ، والـqueue ليس backup ولا يستطيع تسجيل خروج لم يُصوّر.

## التعرف العام مقابل قائمة المطعم

يوجد مساران:

- `reference`: صور مسماة لأصناف مطعم للمقارنة التجريبية؛ لا يوجد dataset تدريب مطعم مقدَّم أو تدريب مخصص فعلي أو دقة معتمدة.
- `detector`: تعيين صنف لفئة أصلية محددة من COCO-SSD عبر `/api/recognition/classes`؛ الفئات الأصلية٨٠، وليست كل الأشياء المعروفة. إذا تعارض تعيين عدة أصناف لنفس الفئة تظهر حالة ملتبسة للمراجعة، ولا نستنتج نوعًا من اختيار عشوائي.

`kind` يميز dish/drink/object/person للكتالوج، لكنه وحده لا يدرب النموذج أو يضيف فئة كشف. يقدر الكاشف أن يرى كوبًا أو زجاجة أو شخصًا ضمن فئاته؛ لا يتعرف تلقائيًا على بشاميل أو محتوى كوب مغلق لمجرد وجود الاسم. أطباق مسطحة أو أصناف شديدة التشابه تحتاج نموذجًا/زاوية/ربط طلب. اختبار الأعداد والمسارات مستقل عن اختبار أسماء الأصناف.

## قرار شراء أو نشر

قبل الاشتراك التجاري: اختر البنية edge+cloud أو cloud inference صراحة، ثم قِس النموذج على جهاز مرشح، واختبر كاميرتين وسرعة المرور٤عناصر، وفشل إنترنت وكهرباء وصورة/قرص، واستعادة DB+media، وصلاحيات API وتوقيت يوم الكاشير. شراء GPU أو VPS لا يكمل هذه العناصر. [دليل النشر](DEPLOYMENT.md)، [التشغيل](OPERATIONS.md)، [التكامل](INTEGRATION_GUIDE.md)، و[المخاطر والصلاحيات](RISK_AND_ACCESS.md) تشكل قائمة المراجعة التنفيذية.
